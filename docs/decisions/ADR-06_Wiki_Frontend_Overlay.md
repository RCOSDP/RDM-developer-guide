# ADR-06 Wiki Frontend Overlay / Wiki フロントエンドのオーバーレイ

> **Summary:** The `wiki-frontend` repository is not a service and not a runtime image. Its Dockerfile is a copy of osf.io's that COPYs osf.io paths the wiki-frontend checkout does not contain (so it cannot be built alone; real install run 4) and that skips every Python step, running only `yarn run webpack-prod` (so its image cannot replace the osf.io image either). We treat it as an *overlay*: its image is built from the osf.io checkout with the wiki-frontend files copied over it, tagged with both commits, and run **once** by the Compose service `wiki_assets`, which copies the webpack output into the named volume `wiki_static`; `web`, `api`, `admin` and `worker` mount that volume read-only. This is the pattern upstream osf.io's own `assets` service uses.
> **概要:** `wiki-frontend` リポジトリはサービスでも実行用イメージでもない。その Dockerfile は osf.io のものの写しで、wiki-frontend の checkout には無い osf.io のパスを COPY する（だから単独では組めない。実機第 4 回）うえ、Python の手順をすべて飛ばして `yarn run webpack-prod` だけを走らせる（だからそのイメージで osf.io のイメージを置き換えることもできない）。これを「オーバーレイ」として扱う。osf.io の checkout に wiki-frontend のファイルを重ねた木からイメージを組み、両コミットをタグに持たせ、Compose サービス `wiki_assets` が **一度だけ** 動かして webpack の出力を名前付きボリューム `wiki_static` へ写す。`web`・`api`・`admin`・`worker` はそのボリュームを読み取り専用で mount する。上流 osf.io 自身の `assets` サービスと同じ型である。

### 1. Context

The manifest ([SPEC-01](../spec/01_manifest.md#english)) listed `wiki-frontend` as a core component with one Compose *service* (a container that Compose starts) named `wiki`, and the installer tried to build it like every other core: clone `RDM-wiki-frontend-dev2027` at the pinned commit and run `docker buildx build` on that checkout.

The fourth real install on Mac Studio (2026-11-06, [DEMO-20](../demo/20_core_install_mac_studio.md)) stopped at `build` with exit 30: *image build failed — component wiki-frontend: docker buildx build exited 1*. BuildKit reported, for dozens of `COPY` lines at once, `failed to calculate checksum ... "/addons/metadata/static": not found`, `"/addons/gitlab/requirements.txt": not found`, `"/addons/zotero/static": not found` and so on.

Reading the two repositories side by side explains it:

- The wiki-frontend checkout contains only `addons/wiki/static/` (the Milkdown editor: `wikiPageMilkdown.js`, `heading.js`, `image.js`, `link.js`, ...), `website/static/js/` (`wikiTree.js`, `fangorn.js`, `pages/wiki-edit-page.js`), `website/static/vendor/knockout-sortable`, `package.json`, `yarn.lock`, `webpack.common.config.js`, `webpack.prod.config.js`, `Dockerfile`, `.jshintrc`, `.travis.yml` and a one-line `README.md`: "This is RDM wiki code for bundle with webpack5".
- Its `Dockerfile` is osf.io's Dockerfile with small edits: `FROM node:21-alpine` instead of `node:12-alpine3.9`, the application's `pip install` of `requirements.txt` and the add-on requirements, `collectstatic` and `pybabel` commented out (the Alpine Python 3 packages themselves are still installed and `python3 -m compileall` still runs), the admin `yarn install` commented out, and `yarn run webpack-prod` left in. It still `COPY`s `./requirements.txt`, `./addons/<name>/requirements.txt` for twenty-odd add-ons, `./admin/package.json ./admin/yarn.lock`, `./website/settings/`, `./api/base/settings/`, and `./addons/<name>/static/` for every add-on. None of these exist in the wiki-frontend tree; all of them exist in `RDM-osf.io-dev2027`. Because the application's Python dependencies are never installed, the image it produces has Node, the `node_modules`, a bare Python 3 and the webpack output — and no Flask or Django that could serve `web`, `api`, `admin` or `worker`.
- Its `package.json` keeps the name `osf` and version `20.14.0` of osf.io and upgrades `webpack` from `3.8.1` to `^5.93.0` (plus `webpack-cli` 5, `terser-webpack-plugin` 5, `assets-webpack-plugin` 7 and the `@milkdown/*` 7.3.6 editor packages). `webpack.common.config.js` keeps a single entry, `wiki-edit-page`, where osf.io's config lists forty pages (and has `wiki-edit-page` commented out), and drops the add-on entry discovery; `webpack.prod.config.js` replaces `UglifyJsPlugin` and `CommonsChunkPlugin` (webpack 3) with `TerserPlugin` and `optimization.splitChunks` (webpack 5).
- Both configs write to the same place: `output.path = <repo>/website/static/public/js` (in the image, `/code/website/static/public/js/`), `filename: '[name].[chunkhash].js'` in production, a `vendor.[hash].js` split chunk, and `SaveAssetsJson()` writes `webpack-assets.json` to the working directory (`/code/webpack-assets.json`). So the overlay build produces `wiki-edit-page.<chunkhash>.js`, `vendor.<hash>.js`, their source maps and a `webpack-assets.json` with those two entries. In the osf.io image the very same directory holds osf.io's forty bundles and its own `webpack-assets.json` (read by `website/util/paths.py` for the `webpack_asset` Mako filter).

So `wiki-frontend` is a *bundle builder* for osf.io's tree: a newer Node base, webpack 5 and the Milkdown editor sources, meant to be laid over the osf.io source before webpack runs. It has no process of its own and its image cannot run the application. Its real-time counterpart, `y-websocket` (the Yjs WebSocket server for co-editing), is a separate repository with its own server and stays a service.

### 3. Decision

1. **Manifest.** A component may carry `overlay_of: "<base id>"` ([SPEC-01 §3](../spec/01_manifest.md#english)). It keeps its own `integration_repo`, `integration_sha`, `upstreams[]` and PR lists, so the weekly integration PR and the upstream tracking ([SPEC-05](../spec/05_upstream_tracking.md)) work unchanged. Its `services[]` are one-shot services. `wiki-frontend` gets `overlay_of: "osf.io"`, `services: ["wiki_static_init", "wiki_assets"]`, `profile: core` and a `note`.
2. **Checker.** `grdm-dev manifest check` adds MC-14: the base exists, is not `infra`, is not an overlay and has no `prebuilt_image`; the overlay is not `infra` and has no `prebuilt_image`; a base takes at most one overlay. The installer refuses an overlay service whose template is not `one_shot: true` (also reported as MC-14).
3. **Build.** `grdm-dev build` builds `osf.io` as before (`grdm-dev/osf.io:<osf_sha12>`). For the overlay it syncs the base checkout too (once per run), recreates `runtime/src/_overlay/wiki-frontend/` as a copy of the osf.io checkout without `.git` with the wiki-frontend files copied over it without `.git` (the overlay's version wins where both have a file: `Dockerfile`, `package.json`, `yarn.lock`, the webpack configs, `addons/wiki/static/*`), and runs `docker buildx build -f <context>/Dockerfile <context>` tagged `grdm-dev/wiki-frontend:<osf_sha12>-<wiki_sha12>` (with `--push`, `ghcr.io/rcosdp/wiki-frontend:<same>`), with the labels `org.gakunin-rdm.overlay-of=osf.io` and `org.gakunin-rdm.base-sha=<osf_sha12>`. The build report row carries `overlay_of`, `base_repo`, `base_sha12` and `image_tag`; `compose render` reads `image_tag`.
4. **Compose.** Two one-shot templates (profile `core`, `one_shot: true`, rendered with `restart: "no"`), both running the overlay image:
   - `wiki_static_init` (review r1 R1-02): a fresh named volume is a bind directory under `runtime/volumes/` created by the host user with `mkdir`, so on a Linux host whose uid is not 1000 the non-root copier cannot write to it. This container runs as root with `cap_drop: [ALL]` and only `CAP_CHOWN` added back — a documented exception in `manifest/hardening.json` (controls `user`, `cap_add`; review 2027-01-31; target M4) — executes only `chown 1000:1000 /wiki_static` and exits. It never runs `chmod`: with only `CAP_CHOWN`, a root process cannot change the mode of a directory owned by another uid (that needs `CAP_FOWNER`), and the bind directory is owned by the host user, so the mode `0755` is set on the host by `compose render` only when it first creates `runtime/volumes/<name>/`; an existing directory (possibly already handed to uid 1000) is left untouched, so re-rendering after the ownership change cannot fail (reviews r2–r4). `chown` is idempotent, so re-runs are safe. `read_only`, `no-new-privileges` and the internal network stay. It touches nothing but the volume mount.
   - `wiki_assets`: runs as `1000:1000` with `cap_drop: [ALL]`, `no-new-privileges`, a read-only root filesystem and `/tmp` on tmpfs (no exception), waits for `wiki_static_init` with `condition: service_completed_successfully`, requires a `wiki-edit-page.<chunkhash>.js` under `/code/website/static/public/js/` (exit 1 otherwise: a missing bundle is never an empty success), proves that it can create a file in `/wiki_static` (a marker file created and removed; `test -w` is a false negative on Docker Desktop for macOS, run 8), copies the directory with `cp -R` (no ownership preservation, which `cp -a` would attempt as uid 1000 on root-owned build output) into the volume at `/wiki_static`, adds `/code/webpack-assets.json` and the unhashed alias `wiki-edit-page.js`, then prunes files that are no longer in the source — copy first, prune after, so a running consumer never sees an empty directory — and exits 0.
   `web`, `api`, `admin` and `worker` mount `wiki_static` read-only at **`/code/website/static/public/js/wiki/`** and list `wiki_assets` in `depends_on` with `condition: service_completed_successfully` (Compose long form; plain dependencies become `condition: service_started`). In the `minimum` profile both one-shots are absent and the dependency is dropped. Because Compose interpolates `$VAR` in every string of the file before the container shell runs (review r1 R1-01 reproduced `ls "" >/dev/null; find "" ...` from `$src`/`$dst`), `compose render` escapes every `$` of a template `command` as `$$`; only `environment` values carry `${KEY}` from `runtime/.env`. A unit test re-implements Compose's interpolation over the rendered file with every key `secrets init` writes, and a second test runs `docker compose config` read-only when the CLI is present.
   **Why a subpath and not the directory itself.** The overlay's `output.path` is the same directory the osf.io image's own `webpack-prod` fills. Mounting the volume *at* `/code/website/static/public/js` would hide osf.io's forty bundles, and copying the overlay's `webpack-assets.json` over osf.io's would break the `webpack_asset` filter for every other page. The overlay image's directory contains only the overlay's output (its config has one entry), so copying it whole into a *subdirectory* is non-destructive: `/static/public/js/wiki/wiki-edit-page.js` is served by the existing static route, the vendor chunk resolves relative to it, and nothing of osf.io is shadowed.
5. **Health and plan.** `health` treats a service with `restart: "no"` as healthy once it has `exited` with code 0 (`health: completed`); still running or non-zero is a failure. `plan` and `compose render` show `wiki_assets` with origin `overlay` and `build_from: RDM-wiki-frontend-dev2027@<sha12> over RDM-osf.io-dev2027@<sha12> (overlay of osf.io)`. The `wiki` template is deleted; [SPEC-02 §4](../spec/02_installer_cli.md#2-en-ports) lists `wiki_static_init` and `wiki_assets` in `core`.

### 4. Consequences

- The osf.io image used by `web`, `api`, `admin` and `worker` is unchanged and still built from osf.io's own Dockerfile. The wiki editor bundle arrives as files in a volume, so a new wiki-frontend commit changes only the overlay tag and the volume contents.
- `wiki-frontend` contributes two one-shot services, no port, and one narrow hardening exception (`wiki_static_init`: root with `CAP_CHOWN` only, for the volume owner fix). The same host-owned-volume question applies to `ember_osf_web_dist` and the other volumes written by non-root services; they are reviewed with the M4 volume-provisioning target of that exception. The acceptance scenario C4 (Wiki collaborative edit, [SPEC-04 §4](../spec/04_acceptance_tests.md#english)) exercises `web`, `y_websocket` and `sharejs`, as before.
- `y-websocket` stays a separate service (`y_websocket`, profile `core`): it is a server, not a bundle.
- **Follow-up, tracked (review r1 R1-03).** osf.io's `addons/wiki/templates/edit.mako` (line 733 at `356a997eb5fe`) loads `/static/js/pages/wiki-edit-page.js` (the raw source), not a built bundle, and osf.io's own webpack config has the `wiki-edit-page` entry commented out. The new bundle is therefore not used by the page until `RDM-osf.io-dev2027` references **`/static/public/js/wiki/wiki-edit-page.js`** (or teaches `webpack_asset` the overlay's `webpack-assets.json` under `/code/website/static/public/js/wiki/`). That change is made in the integration repository, not here; it is listed as an open item on the [status board](../status/README.md) ("統合リポジトリ側の edit.mako 配線（M2 第 5 回で確認）") and in the manifest `note` of `wiki-frontend`. Real install run 5 must show the editor page loading the bundle and its `vendor.<hash>.js` chunk in a browser and the C4 collaborative edit passing before M2 is called working; the overlay build itself (does `yarn run webpack-prod` succeed in the merged tree, is `node:21-alpine` multi-arch), a fresh-volume copy on a host whose uid is not 1000, and a re-run that replaces the bundle under running consumers are confirmed and recorded in [DEMO-20](../demo/20_core_install_mac_studio.md) at the same time.
- Review at M4: when osf.io's Dockerfile is modernized, decide whether the wiki-frontend overlay is merged into the osf.io repository (one webpack build) or stays an overlay; the `overlay_of` and one-shot mechanisms remain available for any other repository of the same shape.

### 1. 背景

manifest（[SPEC-01](../spec/01_manifest.md#japanese)）は `wiki-frontend` をコア部品とし、`wiki` という Compose の「サービス」（Compose が起動するコンテナ）を一つ持たせていた。インストーラーはほかのコアと同じに、`RDM-wiki-frontend-dev2027` を固定コミットで clone し、その checkout で `docker buildx build` を走らせようとした。

Mac Studio での第 4 回実導入（2026-11-06、[DEMO-20](../demo/20_core_install_mac_studio.md)）は `build` で終了 30 になった。「image build failed — component wiki-frontend: docker buildx build exited 1」。BuildKit は何十行もの `COPY` について一度に `failed to calculate checksum ... "/addons/metadata/static": not found`、`"/addons/gitlab/requirements.txt": not found`、`"/addons/zotero/static": not found` などを報告した。

二つのリポジトリを並べて読むと理由が分かる。

- wiki-frontend の checkout にあるのは `addons/wiki/static/`（Milkdown エディタ: `wikiPageMilkdown.js`、`heading.js`、`image.js`、`link.js` など）、`website/static/js/`（`wikiTree.js`、`fangorn.js`、`pages/wiki-edit-page.js`）、`website/static/vendor/knockout-sortable`、`package.json`、`yarn.lock`、`webpack.common.config.js`、`webpack.prod.config.js`、`Dockerfile`、`.jshintrc`、`.travis.yml`、そして一行の `README.md`「This is RDM wiki code for bundle with webpack5」だけである。
- その `Dockerfile` は osf.io の Dockerfile に小さな手を入れたものである。`FROM node:12-alpine3.9` を `node:21-alpine` に、アプリケーションの `requirements.txt` とアドオン要件の `pip install`、`collectstatic`、`pybabel` をコメントアウト（Alpine の Python 3 パッケージ自体は入り、`python3 -m compileall` も走る）、admin の `yarn install` もコメントアウト、`yarn run webpack-prod` は残す。それでも `./requirements.txt`、二十数個のアドオンの `./addons/<name>/requirements.txt`、`./admin/package.json ./admin/yarn.lock`、`./website/settings/`、`./api/base/settings/`、全アドオンの `./addons/<name>/static/` を `COPY` する。どれも wiki-frontend の木には無く、すべて `RDM-osf.io-dev2027` にある。アプリケーションの Python 依存が入らないので、できるイメージには Node と `node_modules`、素の Python 3、webpack の出力しか無く、`web`・`api`・`admin`・`worker` を動かす Flask も Django も入っていない。
- `package.json` は osf.io の名前 `osf` と版 `20.14.0` のまま、`webpack` を `3.8.1` から `^5.93.0` に上げている（`webpack-cli` 5、`terser-webpack-plugin` 5、`assets-webpack-plugin` 7、エディタの `@milkdown/*` 7.3.6 も）。`webpack.common.config.js` は osf.io 側の四十ページのエントリ（そこでは `wiki-edit-page` がコメントアウトされている）を `wiki-edit-page` 一つに絞り、アドオンのエントリ探索を外す。`webpack.prod.config.js` は webpack 3 の `UglifyJsPlugin`・`CommonsChunkPlugin` を webpack 5 の `TerserPlugin`・`optimization.splitChunks` に置き換える。
- 両設定の出力先は同じである。`output.path = <repo>/website/static/public/js`（イメージ内では `/code/website/static/public/js/`）、本番の `filename` は `[name].[chunkhash].js`、`vendor.[hash].js` の分割チャンク、`SaveAssetsJson()` が作業ディレクトリ（`/code/webpack-assets.json`）に `webpack-assets.json` を書く。つまりオーバーレイのビルドは `wiki-edit-page.<chunkhash>.js`、`vendor.<hash>.js`、その source map、二項目だけの `webpack-assets.json` を作る。osf.io のイメージでは同じディレクトリに osf.io の四十本の束と自前の `webpack-assets.json`（`website/util/paths.py` が Mako フィルタ `webpack_asset` のために読む）がある。

つまり `wiki-frontend` は osf.io の木のための「束を組む道具」である。新しい Node ベース、webpack 5、Milkdown エディタのソースを、webpack を走らせる前に osf.io のソースの上へ重ねるためのものだ。自分で動かすプロセスは無く、そのイメージでアプリケーションは動かない。共同編集の相方 `y-websocket`（Yjs の WebSocket サーバ）は独立したリポジトリで自分のサーバを持つので、サービスのままとする。

### 3. 決定

1. **manifest。** 部品は `overlay_of: "<ベースの id>"` を持てる（[SPEC-01 §3](../spec/01_manifest.md#japanese)）。自分の `integration_repo`、`integration_sha`、`upstreams[]`、PR の一覧はそのまま持つので、週次統合 PR と上流追跡（[SPEC-05](../spec/05_upstream_tracking.md)）は変わらず動く。`services[]` は一回限りのサービスである。`wiki-frontend` には `overlay_of: "osf.io"`、`services: ["wiki_static_init", "wiki_assets"]`、`profile: core`、`note` を書く。
2. **検査。** `grdm-dev manifest check` に MC-14 を足す。ベースが存在し、`infra` でなく、オーバーレイでなく、`prebuilt_image` を持たない。オーバーレイは `infra` でなく、`prebuilt_image` を持たない。ベース一つにオーバーレイは最大一つ。インストーラーはテンプレートが `one_shot: true` でないオーバーレイのサービスを拒む（これも MC-14 として報告）。
3. **build。** `grdm-dev build` は `osf.io` をこれまでどおり組む（`grdm-dev/osf.io:<osf の sha12>`）。オーバーレイについては、ベースの checkout も同期し（一回の実行で一度）、`runtime/src/_overlay/wiki-frontend/` を osf.io checkout の `.git` 抜きの写しとして作り直し、その上に wiki-frontend のファイルを `.git` 抜きで重ね（両方にあるファイル `Dockerfile`、`package.json`、`yarn.lock`、webpack 設定、`addons/wiki/static/*` はオーバーレイ側が勝つ）、`docker buildx build -f <context>/Dockerfile <context>` を `grdm-dev/wiki-frontend:<osf の sha12>-<wiki の sha12>`（`--push` では `ghcr.io/rcosdp/wiki-frontend:<同じ>`）のタグと、ラベル `org.gakunin-rdm.overlay-of=osf.io`・`org.gakunin-rdm.base-sha=<osf の sha12>` で走らせる。ビルド報告の行に `overlay_of`、`base_repo`、`base_sha12`、`image_tag` を持たせ、`compose render` は `image_tag` を読む。
4. **compose。** 一回限りのテンプレートを二つ置く（profile `core`、`one_shot: true`、`restart: "no"` で出力）。どちらもオーバーレイのイメージを動かす。
   - `wiki_static_init`（レビュー r1 R1-02）: 新しい名前付きボリュームは `runtime/volumes/` 配下にホストの利用者が `mkdir` で作る bind ディレクトリなので、uid が 1000 でない Linux ホストでは非 root の写し手が書けない。このコンテナは root で `cap_drop: [ALL]` に `CAP_CHOWN` だけを戻して動き（`manifest/hardening.json` に記した例外。controls は `user`・`cap_add`、見直し 2027-01-31、目標 M4）、`chown 1000:1000 /wiki_static` だけを実行して終了する。`chmod` は行わない。`CAP_CHOWN` しか無い root は他の uid が所有するディレクトリのモードを変えられず（`CAP_FOWNER` が要る）、bind ディレクトリの所有者はホストの利用者なので、モード `0755` は `compose render` が `runtime/volumes/<name>/` を初めて作るときだけホスト側で設定し、既存のディレクトリ（すでに uid 1000 に渡っているかもしれない）には触れないので、所有者が変わった後の再描画が失敗することはない（レビュー r2〜r4）。`chown` は冪等なので再実行しても安全。`read_only`・`no-new-privileges`・内部ネットワークはそのまま。ボリュームの mount 以外には触れない。
   - `wiki_assets`: 利用者 `1000:1000`、`cap_drop: [ALL]`、`no-new-privileges`、読み取り専用ルート、tmpfs の `/tmp`（例外なし）で動き、`wiki_static_init` を `condition: service_completed_successfully` で待ち、`/code/website/static/public/js/` に `wiki-edit-page.<chunkhash>.js` があることを要求し（無ければ exit 1。束が無いのに成功にはしない）、`/wiki_static` にファイルを作れることを証明し（目印ファイルを作って消す。macOS の Docker Desktop では `test -w` が偽陰性になる。第 8 回）、`cp -R`（所有権を保たない。uid 1000 の `cp -a` は root 所有のビルド成果で失敗しうる）でディレクトリを `/wiki_static` のボリュームへ写し、`/code/webpack-assets.json` とハッシュ無しの別名 `wiki-edit-page.js` を加え、元に無くなったファイルを後から消す（先に写し、後で間引く。動いている利用側が空のディレクトリを見ることはない）、そして 0 で終了する。
   `web`・`api`・`admin`・`worker` は `wiki_static` を **`/code/website/static/public/js/wiki/`** に読み取り専用で mount し、`depends_on` に `wiki_assets` を `condition: service_completed_successfully` で載せる（Compose の長い形。普通の依存は `condition: service_started` になる）。`minimum` プロファイルでは二つの一回限りサービスが無く、依存は落とされる。Compose はファイル中のすべての文字列の `$VAR` をコンテナのシェルより前に展開する（レビュー r1 R1-01 は `$src`/`$dst` から `ls "" >/dev/null; find "" ...` を再現した）ので、`compose render` はテンプレートの `command` の `$` をすべて `$$` にエスケープする。`runtime/.env` の `${KEY}` を運ぶのは `environment` の値だけ。単体試験は `secrets init` が書く全キーで Compose の展開を再実装して出力ファイルに適用し、もう一つの試験は CLI があるときに `docker compose config` を読み取り専用で走らせる。
   **なぜディレクトリそのものでなく下位パスか。** オーバーレイの `output.path` は、osf.io のイメージ自身の `webpack-prod` が満たすディレクトリと同じである。ボリュームを `/code/website/static/public/js` に mount すると osf.io の四十本の束が隠れ、オーバーレイの `webpack-assets.json` で osf.io のものを上書きすれば他の全ページの `webpack_asset` フィルタが壊れる。オーバーレイのイメージのそのディレクトリにはオーバーレイの出力しか無い（設定のエントリは一つ）ので、丸ごと「下位ディレクトリ」へ写すのは非破壊である。`/static/public/js/wiki/wiki-edit-page.js` は既存の静的ルートで配信され、vendor チャンクはそれに相対で解決し、osf.io のものは何も隠れない。
5. **health と plan。** `health` は `restart: "no"` のサービスを、終了コード 0 の `exited` で健康（`health: completed`）とみなす。まだ動いている、または 0 以外なら失敗。`plan` と `compose render` は `wiki_assets` を origin `overlay`、`build_from: RDM-wiki-frontend-dev2027@<sha12> over RDM-osf.io-dev2027@<sha12> (overlay of osf.io)` で示す。テンプレート `wiki` は削除し、[SPEC-02 §4](../spec/02_installer_cli.md#2-ja-ports) は `core` に `wiki_static_init` と `wiki_assets` を載せる。

### 4. 結果

- `web`・`api`・`admin`・`worker` が使う osf.io のイメージは変わらず、osf.io 自身の Dockerfile から組まれる。Wiki エディタの束はボリュームのファイルとして届くので、wiki-frontend の新しいコミットが変えるのはオーバーレイのタグとボリュームの中身だけである。
- `wiki-frontend` が持ち込むのは一回限りのサービス二つで、ポートは無く、hardening の例外は狭いもの一つ（`wiki_static_init`: ボリュームの所有者を直すための root と `CAP_CHOWN` のみ）。ホスト所有のボリュームという同じ問題は `ember_osf_web_dist` など非 root サービスが書く他のボリュームにもあり、その例外の M4 目標（ボリューム準備段）で一緒に見直す。受入シナリオ C4（Wiki 共同編集、[SPEC-04 §4](../spec/04_acceptance_tests.md#japanese)）はこれまでどおり `web`・`y_websocket`・`sharejs` を使う。
- `y-websocket` は独立サービス（`y_websocket`、profile `core`）のまま。サーバであって束ではない。
- **追跡中の残件（レビュー r1 R1-03）。** osf.io の `addons/wiki/templates/edit.mako`（`356a997eb5fe` の 733 行）は `/static/js/pages/wiki-edit-page.js`（生のソース）を読み込み、組んだ束ではない。osf.io 自身の webpack 設定でも `wiki-edit-page` のエントリはコメントアウトされている。したがって `RDM-osf.io-dev2027` が **`/static/public/js/wiki/wiki-edit-page.js`** を参照する（または `/code/website/static/public/js/wiki/` のオーバーレイの `webpack-assets.json` を `webpack_asset` に読ませる）までは、新しい束はページに使われない。この変更は統合リポジトリ側で行い、ここでは行わない。[進捗ボード](../status/README.md)の残件（「統合リポジトリ側の edit.mako 配線（M2 第 5 回で確認）」）と `wiki-frontend` の manifest `note` に載せた。実機第 5 回で、エディタのページが束と `vendor.<hash>.js` チャンクをブラウザで読み込み、C4 の共同編集が通ることを示してから M2 を動作したと呼ぶ。オーバーレイのビルドそのもの（重ねた木で `yarn run webpack-prod` が通るか、`node:21-alpine` が多アーキテクチャか）、uid が 1000 でないホストでの新規ボリュームへの写し、動いている利用側の下で束を置き換える再実行も、同時に確かめて [DEMO-20](../demo/20_core_install_mac_studio.md) に記録する。
- M4 で見直す。osf.io の Dockerfile を近代化する時に、wiki-frontend のオーバーレイを osf.io のリポジトリに統合する（webpack ビルドを一つにする）かオーバーレイのまま置くかを決める。`overlay_of` と一回限りのサービスの仕組みは、同じ形のほかのリポジトリにも使える。

| Overlay | A set of files laid over another repository's tree before the image is built; its image is a build tool, not a server. | イメージを組む前にほかのリポジトリの木の上に重ねるファイルの組。そのイメージはビルド道具でサーバではない。 |
