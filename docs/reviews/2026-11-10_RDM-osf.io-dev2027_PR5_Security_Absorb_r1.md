### Verdict and scope

**Request changes for R1.** R2 and R3 are confirmed pre-existing gaps, not regressions introduced by this PR. They need explicit follow-up if the acceptance claim is repository-wide signature hardening. The owner's 2026-11-10 decision to absorb the source fixes is accepted; the closed-unmerged source PR status is not a finding.

The review used a fresh scratch clone and read-only `gh` queries. No repository commits, pushes, approvals, merges, or closures were performed. No Docker commands or runtime environment files were used. Only this record and the requested single PR comment are deliverables.

### R1 — [P2 / Medium] A confirmation save can roll back the replay counter

Locations: `addons/twofactor/models.py:79–96`, `addons/twofactor/views.py:22–24`, `api/users/serializers.py:540–544`.

The conditional database update correctly stops two stale instances from consuming the same step when `allow_same_step=False`. However, both confirmation callers subsequently call unrestricted `save()`. `BaseModel.save()` delegates to Django without limiting fields (`osf/models/base.py:133–141`). A delayed confirmation for step N can overwrite the newer counter written by another request for N+1. A subsequent strict verification of N+1 then succeeds again.

Reproduction used the exact `verify_code` method extracted from the head, real oath 1.4.2 codes, and a minimal Django model with the same fields in an isolated SQLite memory database. This is a deterministic interleaving demonstration, not a production PostgreSQL concurrency test. At fixed time 1800000000, A accepts N, B accepts N+1, A sets `is_confirmed` and saves all fields, then C accepts the already-consumed N+1. The database counter changes from 60000001 to 60000000. The accepted drift window makes both codes valid at that fixed time.

Persist only the confirmation field after verification, or make verification and confirmation one transaction with suitable locking. Ensure counter writes remain monotonic and add a test that includes the callers' save, not only two `verify_code` calls. Review concurrent secret reset/deletion as part of that transaction design; the update currently predicates only on primary key and counter, not the verified secret. The reset race was not independently reproduced.

### R2 — [P2 / Medium, pre-existing] Three HMAC checks still use ordinary comparison

Locations: `addons/github/utils.py:43`, `addons/gitlab/utils.py:42`, `website/conferences/message.py:54`.

The GitHub and GitLab hook validators compare `digest != signature`; Mailgun's validator compares `signature != self.form['signature']`. These functions are used by their receiving views. All three files are identical to the base. Thus the new `framework/auth/signing.py` helper correctly fixes its two verification methods, but does not establish constant-time comparison everywhere. Replace these remaining comparisons with the shared normalized helper or same-type `hmac.compare_digest`, and test that the constant-time primitive is actually called. No practical network timing exploit was attempted or claimed.

### R3 — [P2 / Medium, pre-existing] Nextcloud's constant-time comparison has mismatched types

Location: `addons/nextcloudinstitutions/views.py:57–58`.

`hexdigest()` returns text, while the supplied signature is encoded to bytes. `hmac.compare_digest(bytes, str)` raises `TypeError`, including for a correct signature. This file is identical to the base. Normalize both operands to the same type and test a valid notification and an invalid signature. A local expression reproduced the exception; the complete notification route was not executed.

### Assessment of each absorbed fix

**SSRF.** Dataset API validation is followed by worker-side validation of the page, each `contentUrl`, and every redirect. `safe_fetch.resolve_and_validate` validates every resolved address, rejects disagreements between URL parsers, and pins the chosen numeric address in `_new_conn`. This removes the second hostname resolution that enables DNS rebinding. HTTP redirects are followed manually; private redirect targets are rejected before connection. Environment proxies are disabled, while CA bundle selection is retained. Dataverse replaces the requests references in the three pinned client-library modules with the same transport protections. Cross-origin redirects strip ordinary authorization/cookie headers and explicit auth, and reject replay of non-GET bodies unless the redirect becomes GET.

IPv6 loopback, unique-local, link-local, mapped IPv4, 6to4, and Teredo are considered by the address checks. Unspecified `0.0.0.0` and decimal loopback `2130706433` were rejected in direct local probes. Hex loopback and mapped loopback were also rejected. On this macOS resolver, `0177.0.0.1` resolves to public `177.0.0.1`; it is allowed and pinned to that public address, rather than subsequently reinterpreted as loopback. No SSRF bypass was established in the reviewed dataset/Dataverse paths. This does not cover GitLab host selection or WaterButler.

**Dataverse compatibility.** The default `DATAVERSE_ALLOWED_HOSTS=[]` denies private hosts even for previously stored accounts. Register the institution's actual host before deployment. Exact names, a name with a port, and leading-dot domain entries are supported; a host-only match also allows that host on other ports. The exception permits private addresses, but does not permit loopback, link-local, unspecified, multicast, or reserved addresses. Redirect destinations need their own matching permission. `validate_host` returns early for an allowlisted host, but the transport still resolves and enforces those exclusions before connection. An allowlist entry alone therefore does not make a loopback Dataverse usable. Use narrow institution-controlled entries.

**HMAC.** Both `Signer` verification methods use the new helper; it normalizes bytes/text and rejects non-string values. Cron signed URLs, IQBRIMS, Crossref, Dropbox Business, and throttling comparisons already call `compare_digest`. R2 and R3 qualify any claim that every signature verifier is correct. Existing valid/invalid signature tests alone would also pass an implementation using ordinary equality; they do not prove constant-time execution.

**TOTP.** The stored nullable counter and conditional update provide useful cross-instance protection. Older steps are rejected. The current step remains reusable by default for per-request API/Basic authentication, intentionally; strict same-step rejection is limited to setup confirmation. This is not universal one-use login protection. `on_add` and `on_delete` reset the counter. R1 defeats monotonicity across the complete confirmation flow. Existing stale-instance tests stop before the subsequent unrestricted save. Rejected older codes continue to count toward lockout under the existing callers; their comments about unavailable rejection reasons are stale, as already disclosed in the PR.

**CSRF: all five exemptions checked.** In `admin/rdm_addons/api_v1/views.py`, `OAuthView` has DELETE; `AccountsView` has GET/POST; `ManageView` and `OrganizationView` have GET/PUT/DELETE. The fifth is `admin/rdm_addons/oauth/views.py:AccountsView`, with DELETE. All retain permission mixins. The three body-writing methods require JSON, rejecting form-compatible media types. Plain browser forms cannot issue PUT/DELETE, and cross-origin JavaScript requires successful preflight for JSON/PUT/DELETE. No method-override path was found in the inspected dispatch/middleware paths. The code therefore blocks the ordinary form-post attack without adding a CSRF token. This relies on cross-origin requests remaining restricted and trusted origins remaining trustworthy; no browser or deployed CORS test was run. GET helpers may create a missing default option record, but the inspected GET handlers do not perform the targeted account/project association changes. The five exemptions alone are not an established remaining exploit.

**SQL identifiers.** Provider table names and the branch column are composed with `psycopg2.sql.Identifier`; rendering uses the live cursor connection. Query relationships are preserved. The hostile-column test distinguishes a quoted undefined column (`42703`) from the old SQL parse failure, but does not prove a formerly exploitable user-input path. The provider mapping already restricts inputs. This is appropriate defense in depth.

**Compose.** The RabbitMQ management port is now exactly `127.0.0.1:15672:15672`. Other published services remain exposed on all interfaces, explicitly documented as development-only. The change does not claim to harden the whole stack. No Docker state was inspected or changed.

**Migration.** `addons_twofactor/0005_usersettings_totp_last_counter` depends on `0004_rename_deleted_field` and adds one nullable `BigIntegerField`, without a default or data migration. Model and migration agree. Existing rows start with no replay history. Apply it before code requiring the column, and avoid a mixed old/new writer deployment because old processes do not enforce the new replay rule. Rollback removes replay history and requires the old application version. A table lock is still needed for schema change. Production migration timing and PostgreSQL forward/reverse execution were not independently tested; the successful disposable-DB migration results in the PR are author-reported evidence.

### 判定と範囲

**R1 の修正を要求する。** R2 と R3 は既存の不足であり、この PR が導入した退行ではない。リポジトリ全体の署名強化を受入条件とする場合は、追跡対応を明示する必要がある。2026-11-10 の所有者による取り込み判断を前提とし、出典 PR の未マージ閉鎖そのものは指摘にしない。

### R1 — [P2 / 中] 設定確認の保存が再利用防止カウンタを巻き戻せる

対象: `addons/twofactor/models.py:79–96`、`addons/twofactor/views.py:22–24`、`api/users/serializers.py:540–544`。

条件付き DB 更新は、古いインスタンス二つが `allow_same_step=False` で同一ステップを消費することを防ぐ。しかし設定確認の両呼び出し元は、その後にフィールド指定のない `save()` を行う。`BaseModel.save()` もフィールドを限定せず Django に委譲する（`osf/models/base.py:133–141`）。ステップ N の設定確認が遅れると、別の要求が記録した N+1 を古い N で上書きし、その後 N+1 を厳密モードでも再利用できる。

head の `verify_code` をそのまま抽出し、oath 1.4.2 の実コードと同じフィールドを持つ最小 Django モデルを独立 SQLite メモリ DB で実行した。本番 PostgreSQL の並行試験ではなく、処理順を固定した再現である。時刻 1800000000 で A が N、B が N+1 を受理した後、A が `is_confirmed` を設定して全フィールドを保存すると、C が使用済み N+1 を再度受理した。カウンタは 60000001 から 60000000 に戻った。許容時刻ずれにより、この固定時刻でも両コードは有効になる。

検証後は確認済みフィールドだけを保存するか、検証と確認を適切なロック付きの一つのトランザクションにすること。カウンタが後退しないようにし、二つの `verify_code` だけでなく呼び出し元の保存まで含む試験を追加すること。更新条件には主キーとカウンタしかなく検証した秘密値を含まないため、その設計では秘密値の再設定・削除との競合も検討すること。再設定競合そのものは独立再現していない。

### R2 — [P2 / 中、既存] HMAC の通常比較が三か所残る

対象: `addons/github/utils.py:43`、`addons/gitlab/utils.py:42`、`website/conferences/message.py:54`。

GitHub・GitLab は `digest != signature`、Mailgun は `signature != self.form['signature']` を使い、受信 view から呼ばれる。三ファイルとも base と同一である。`framework/auth/signing.py` の二つの検証経路の修正は妥当だが、全署名検証を定数時間にするものではない。正規化した共通ヘルパーまたは同じ型の `hmac.compare_digest` に統一し、その関数が呼ばれる試験を追加すること。ネットワーク越しの実用的な時間差攻撃は試行も実証もしていない。

### R3 — [P2 / 中、既存] Nextcloud の定数時間比較は型が一致しない

対象: `addons/nextcloudinstitutions/views.py:57–58`。

`hexdigest()` は文字列だが、入力署名は bytes に変換される。`hmac.compare_digest(bytes, str)` は正しい署名でも `TypeError` になる。このファイルも base と同一である。両辺を同じ型に統一し、正しい通知と不正署名の試験を追加すること。式単体の例外は再現したが、通知ルート全体は実行していない。

### 取り込まれた各修正の評価

**SSRF。** データセット API の検証に加え、worker がページ、各 `contentUrl`、各リダイレクトを再検証する。`safe_fetch.resolve_and_validate` は全解決先を検証し、URL 解釈の不一致を拒否し、選んだ数値 IP を `_new_conn` に固定する。DNS rebinding に必要な二度目のホスト名解決を排除する構造である。リダイレクトは手動処理され、私設の転送先は接続前に拒否される。環境プロキシは使わず、CA バンドル設定は維持する。Dataverse は固定されたクライアント依存の三モジュールの requests 参照をこの安全な転送処理に置換する。別 origin への転送では認証・Cookie ヘッダーと明示的認証を除き、GET に変換されない非 GET 本文の再送を拒否する。

IPv6 の loopback、unique-local、link-local、IPv4-mapped、6to4、Teredo を検査する。直接のローカル試験で `0.0.0.0` と十進数 loopback `2130706433` を拒否した。16進 loopback と mapped loopback も拒否した。この macOS の名前解決では `0177.0.0.1` は公開 IP `177.0.0.1` になり、その公開 IP に固定されるため、その後 loopback として再解釈されない。対象のデータセット・Dataverse 経路で迂回は確認しなかった。GitLab のホスト選択と WaterButler はこの結論の対象外。

**Dataverse の互換性。** 既定の `DATAVERSE_ALLOWED_HOSTS=[]` では既存アカウントも私設ホストへ接続できなくなる。配備前に機関の実ホストを登録すること。完全一致名、ポート付き名、先頭ドットのドメイン指定が使える。ホスト名のみの一致は別ポートも許容する。例外は私設 IP を許すが loopback、link-local、未指定、multicast、予約 IP は許さない。転送先も独自に許可条件を満たす必要がある。許可ホストに対して `validate_host` は早期 return するが、実転送時に名前解決と除外条件の検査が行われる。そのため許可リストだけで loopback 上の Dataverse を使えるようにはならない。機関が管理する範囲に絞ること。

**HMAC。** `Signer` の両検証は新ヘルパーを使い、bytes と文字列を正規化し、それ以外の型を拒否する。cron 署名 URL、IQBRIMS、Crossref、Dropbox Business、throttling は既に `compare_digest` を呼ぶ。全検証が正しいという主張には R2 と R3 が残る。正解・不正解を確認する既存試験だけでは通常の等値比較でも通るため、定数時間であることは検証できない。

**TOTP。** NULL 可の保存カウンタと条件付き更新はインスタンス間で有効であり、古いステップを拒否する。API・Basic 認証は毎要求で送信するため、既定では同一ステップを再利用できる設計であり、同一ステップの厳密拒否は設定確認に限定される。ログイン全般での一回限り保証ではない。追加・削除時にはカウンタをリセットする。ただし確認全体では R1 により単調性が破れる。既存の stale-instance 試験は後続保存前に終わる。古いコードの拒否も既存の呼び出し元でロックアウト失敗回数に数えられ、拒否理由が公開されないというコメントは古い。これは PR でも開示済み。

**CSRF: 残る五か所を確認。** `admin/rdm_addons/api_v1/views.py` の `OAuthView` は DELETE、`AccountsView` は GET/POST、`ManageView` と `OrganizationView` は GET/PUT/DELETE。五つ目の `admin/rdm_addons/oauth/views.py:AccountsView` は DELETE。いずれも権限 mixin を維持する。本文を書き込む三メソッドは JSON を必須にしてフォームの media type を拒否する。通常のブラウザフォームは PUT/DELETE を送れず、別 origin の JavaScript による JSON/PUT/DELETE は preflight の成功が必要である。調査した dispatch・middleware には method override 経路を見つけなかった。CSRF token の追加なしで通常のフォーム POST 攻撃を止めるが、別 origin の通信制限と信頼 origin の安全性に依存する。ブラウザや配備済み CORS の実験は未実施。GET の補助処理は未作成の既定設定レコードを作る場合があるが、調査した GET は対象のアカウント・プロジェクト関連付け変更を行わない。五つの例外が残る事実だけでは攻撃成立とは判定しない。

**SQL 識別子。** provider のテーブル名と branch 列名を `psycopg2.sql.Identifier` で構成し、実 cursor の接続で文字列化する。結合関係は維持する。悪意ある列名の試験は引用された未定義列 `42703` と旧実装の構文エラーを区別するが、旧実装の利用者入力からの攻撃成立を示すものではない。provider は既にマッピングで絞られており、多層防御として妥当。

**Compose。** RabbitMQ 管理ポートは正確に `127.0.0.1:15672:15672` になった。他の公開サービスは全インターフェースのままで、開発専用という注意書きを追加している。スタック全体の強化を意味しない。Docker 状態は参照も変更もしていない。

**マイグレーション。** `addons_twofactor/0005_usersettings_totp_last_counter` は `0004_rename_deleted_field` に依存し、NULL 可の `BigIntegerField` 一列だけを追加する。既定値とデータ移行はなくモデルと一致する。既存行は使用履歴なしから始まる。列を必要とするコードより先に適用し、旧プロセスは新しい再利用ルールを守らないため新旧 writer 混在を避けること。巻き戻すと履歴が失われ、旧アプリケーションが必要になる。スキーマ変更にはテーブルロックが必要。本番での時間と PostgreSQL 上の正逆適用は独立検証していない。PR 内の使い捨て DB での成功は作成者の報告として扱う。

## Glossary / 用語

| Term | English note | 日本語注 |
|---|---|---|
| SSRF | Making a server fetch an address chosen by an attacker. | 攻撃者が選んだ接続先へサーバー自身をアクセスさせること。 |
| DNS rebinding | Changing the address behind a name between checking and connecting. | 検査時と接続時の間に名前の指す IP を変えること。 |
| HMAC | A secret-key calculation used to check that a message is authentic. | 秘密の鍵を使い、メッセージが本物かを確かめる計算。 |
| Constant-time comparison | Comparing secrets without stopping at the first differing character. | 最初に違う文字で打ち切らず秘密値を比較する方法。 |
| TOTP / replay | A time-based code / using an already accepted code again. | 時刻で変わるコード／受理済みのコードをもう一度使うこと。 |
| CSRF / preflight | Tricking a browser into an unwanted action / its permission check before certain cross-site requests. | ブラウザをだまして操作させる攻撃／特定の別サイト要求の前に行う許可確認。 |
| Migration | A controlled change to the database structure. | DB の構造を手順に沿って変えること。 |
| Race / monotonic counter | An outcome depending on overlapping operations / a count that never moves backward. | 重なる処理の順番で結果が変わること／後退しないカウンタ。 |
| P2 / Medium | A defect to fix, without claiming an immediate critical compromise. | 修正すべき欠陥。即時の致命的侵害を意味しない。 |
