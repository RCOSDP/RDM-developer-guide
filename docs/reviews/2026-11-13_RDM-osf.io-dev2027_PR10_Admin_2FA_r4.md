### R2-01 closure and access boundary

`admin/base/settings/defaults.py:232–245` installs SessionMiddleware, AuthenticationMiddleware, TwoFactorSessionMiddleware, MessageMiddleware, then AdminLoginRequiredMiddleware. The two-factor check runs in the request chain before the global guard's `process_view`. The intervening message middleware does not execute the protected view.

`admin/common_auth/middleware.py:20–25` logs out inactive users and sessions whose marker does not verify for the current user. `admin/base/middleware.py:32–43` then redirects anonymous users, logs out inactive users defensively, rejects authenticated users without staff/superuser rights with 403, and permits active staff/superusers. This now protects views without their own check, including `CannotDeleteInstitution`.

The reviewer used real Django 2.2.28 request handling and unchanged extracted production middleware, verification functions and ODMBackend with a stand-in Django User model, SQLite sessions, and an instrumented protected view. ### Public routes and second-step integrity

`admin/common_auth/urls.py:13–19` marks exactly five authentication views public: LoginView, ShibLoginView, TwoFactorVerifyView, TwoFactorSetupView, and logout_user. Replacing `_before_login` with `login_not_required` preserves the callback attribute `login_required = False`. Public status belongs to the resolved callback, not an `/account/login` path prefix, so the exception does not expose other admin views. RecoveryCodesView is unmarked and retains LoginRequiredMixin plus an active-admin check (`views.py:303–313`); regeneration also requires a current TOTP.

These five authentication views are not the entire site's public set. The existing signed GatherView and external_acc_update callbacks, password-reset views, and the admin login redirect/disabled callback remain explicit exceptions. The resolver-enumeration test compares exact sets, including third-party callbacks, rather than accepting an arbitrary subset. The third-party AdminSite.login callback appears in resolver enumeration but the earlier exact `/admin/login/` route shadows it.

Both second-step views validate a pending sign-in before handling GET/POST. `two_factor.get_pending` checks the stage, expiration, active admin rights, password hash and open database record. Verify requires confirmed TOTP settings; setup rejects an already confirmed account and binds confirmation to the secret shown for that pending sign-in. Completion closes the pending record before login. Missing/expired/wrong-stage pending state does not authenticate. Setup's explicit grace option remains disabled by default and is deadline-bound when configured; it is not an accidental bypass introduced by the public decorator. Existing HTTP tests exercise missing first step, wrong user, expiration, replay, grace expiry/removal, and recovery access with the production middleware chain.

### Tests, Shibboleth and direct admin login

The only differences from #8's `admin_tests/base/test_middleware.py` are imports, three exact public-set additions, and setting a user-bound verification marker in the non-staff HTTP test. The latter is necessary to reach the authorization check: without it, the preceding two-factor middleware logs the session out and the expected response is 302. The assertion remains 403, and direct middleware staff/superuser, anonymous, inactive-account and signed-callback assertions remain intact. Existing #10 tests independently require unverified sessions and mismatched markers to be logged out. These adjustments do not weaken #8's guarantees.

`ShibLoginView` and the two-factor core are unchanged from r3. Shibboleth in default `totp` mode starts a pending sign-in; only the second step authenticates. Explicit `idp` mode requires an allowed server-environment MFA context, rejects client context headers and an HTTP-header source configuration, and sets the user-bound verified marker only after that check. Existing Shibboleth HTTP tests cover both modes and spoofing. Trust in the deployment's authenticated Shibboleth identity attributes remains a deployment prerequisite; r4 does not claim a live identity-provider test.

`admin/base/urls.py:19–25` keeps `admin_site_login` public and routes both GET and POST to the ordinary two-step login without authenticating from posted passwords. It carries `next` as a parameter of that local login URL; the login flow subsequently filters it through `safe_next`. The password-disabled configuration returns 404 through the earlier disabled callback. These functions and their route precedence are unchanged by the merge.

### 公開経路と第二段階の完全性

`admin/common_auth/urls.py:13–19` で公開指定される認証ビューは LoginView、ShibLoginView、TwoFactorVerifyView、TwoFactorSetupView、logout_user の正確に5つ。`_before_login` を `login_not_required` に置き換えても callback の `login_required = False` は維持される。公開性は解決された callback に属し、`/account/login` というパス接頭辞には属さないため、他の管理ビューは公開されない。RecoveryCodesView は無指定であり LoginRequiredMixin と有効な管理者の検査も維持する（`views.py:303–313`）。再発行には現在の TOTP も必要。

この5つはサイト全体の公開集合ではない。既存の署名付き GatherView と external_acc_update、パスワード再設定ビュー、管理ログインの転送／無効化 callback も明示的な例外として残る。resolver 列挙試験は第三者 callback を含め正確な集合を比較し、任意の部分集合を許容しない。第三者の AdminSite.login callback は列挙されるが、先に定義された完全一致の `/admin/login/` が実際のアクセスを受ける。

両第二段階ビューは GET/POST を処理する前に保留ログインを検証する。`two_factor.get_pending` は段階、期限、有効な管理権限、パスワードハッシュ、未終了 DB レコードを確認する。verify は確認済み TOTP 設定を要求し、setup は設定済みアカウントを拒否し、その保留ログインに表示した秘密鍵に確認を結び付ける。完了時は保留レコードを閉じてからログインする。保留の欠落・期限切れ・段階違いでは認証されない。明示的な猶予設定は既定で無効で、設定時も期限付きであり、公開 decorator により新たに生じた迂回ではない。既存 HTTP 試験は製品ミドルウェア列で第一段階の欠落、別ユーザー、期限切れ、再利用、猶予期限／解除、回復コードへのアクセスを検査する。

### 試験、Shibboleth、直接の管理ログイン

#8 の `admin_tests/base/test_middleware.py` との差は import、正確な公開集合への3項目追加、非staff HTTP 試験への本人の検証印設定だけ。最後の調整は権限検査に到達するために必要であり、印がなければ先行する二要素認証ミドルウェアがログアウトさせ 302 になる。期待値は 403 のままであり、直接ミドルウェアを呼ぶ staff/superuser、匿名、無効化アカウント、署名 callback の検査も維持される。既存 #10 試験は未検証セッションと別人の印をログアウトさせることを独立して要求する。この調整は #8 の保証を弱めない。
