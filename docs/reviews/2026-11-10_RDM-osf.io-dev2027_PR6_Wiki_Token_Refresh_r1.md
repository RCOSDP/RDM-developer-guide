### Verdict and permission checks

**Pass**, with R1-01 [P3] below. `views.py:265–299` checks login and current WRITE permission, with the existing publicly-editable Wiki exception for logged-in users. Anonymous callers receive 401; non-contributors, removed writers and read-only contributors receive 403 on ordinary wikis. Publicly editable wikis intentionally allow those logged-in users. Registration requests are rejected by `must_not_be_registration`; the shared predicate also rejects an archiving registration that the decorator permits through. Deleted nodes are rejected by `must_be_valid_project` through `get_or_http_error` (410, or 451 for suspended/deleted nodes); missing nodes return 404. The page guard is not identical, but normal conversion to private calls the wiki privacy hook, which clears and saves publicly-editable status. No reachable private-wiki bypass was demonstrated.

Room lookup does not create a new room; absent room gives 404 and absent signing secret gives 503. The room identifier matches the original page and the renewal response. HS256 and the existing default lifetime of eight hours are unchanged (`utils.py:71–95`, `settings/defaults.py:12–14`). Expiry is checked on new connections only: an already-issued token can remain usable until expiry after permission removal, and established connections are not revoked by this endpoint. This is the existing contract, not immediate permission revocation.

### R1-01 [P3]: make response storage and POST provenance explicit

`views.py:299` returns the bearer credential without `Cache-Control: no-store`; the JSON renderer and inspected Flask handlers do not add it. Add explicit no-store and test the final response headers. POST without explicit freshness is not ordinarily reusable by HTTP caches, so this review does not claim a demonstrated shared-cache leak.

The route accepts POST, does not inspect the body/content type, and has no explicit CSRF verification. `framework/csrf/handlers.py` supplies a cookie but does not validate the request token; merely calling `$osf.postJSON` is not server protection. A cross-site simple form can trigger issuance if session cookies are sent. However, this endpoint changes no application state, creates no room and returns JSON; same-origin policy prevents an unrelated site from reading the credential absent a separate cross-origin exposure. No credential theft or state-changing CSRF was demonstrated. Prefer explicit CSRF/origin verification for POST, or document a safe read-only GET design with no-store and compatible client changes. Test the chosen method, origin and session-cookie behavior. Do not describe this POST as CSRF-protected today.

### Evidence and limits

Read the complete diff, routing/renderer, auth, project/database guards and privacy hooks. An AST-extracted real view and predicate with stub models passed nine permission/result cases, including registration defense in depth; this is not a framework integration test. Existing new tests cover writer/anonymous/outsider/reader/removal/public editing/missing room/missing secret/method, but do not cover deleted/registration nodes or cache/CSRF behavior. The author's reported 13 pytest cases were not independently rerun: the required OSF database/runtime was not started. The frontend real-provider probe validated the response contract with a stub renewal callback.

Only private scratch files, this review record and one requested PR comment are changed. No commit, push, merge, approval, Docker state change or runtime/.env access was performed.

### 判定と権限確認

**pass。** 下記R1-01［P3］の助言あり。`views.py:265–299` はログインと現在のWRITE権限を確認し、既存の公開編集Wikiではログイン済み利用者を例外として許す。通常のWikiでは匿名401、非貢献者・除名された編集者・読取専用貢献者403。公開編集Wikiではそれらのログイン済み利用者も意図どおり許可する。登録は`must_not_be_registration`で拒否し、同decoratorが通すアーカイブ中の登録も共通判定で拒否する。削除ノードは`must_be_valid_project`から`get_or_http_error`を経て410（停止かつ削除なら451）、存在しないノードは404になる。ページのguardと完全同一ではないが、通常の非公開化はWikiのprivacy hookで公開編集状態を解除・保存する。到達可能な非公開Wiki迂回は実証されなかった。

部屋参照は新規作成をせず、部屋なし404、署名秘密なし503。部屋IDは元ページと更新応答で一致する。HS256と既定8時間の期限は変更していない（`utils.py:71–95`、`settings/defaults.py:12–14`）。期限検査は新規接続時のみ。権限取消後も既発行トークンは期限まで利用可能で、接続済みの利用者をこのAPIは排除しない。既存の契約であり、即時の権限失効を提供するものではない。

### R1-01［P3］：応答保存とPOST呼出元を明示する

`views.py:299` はbearer資格情報を`Cache-Control: no-store`なしで返し、JSON rendererと調査したFlask handlerも補っていない。明示的なno-storeと最終応答headerの試験を追加してほしい。明示的な鮮度指定のないPOSTは通常HTTPキャッシュで再利用されないため、共有キャッシュからの漏洩を実証した指摘ではない。

POSTはbodyやcontent typeを検査せず、明示的なCSRF検証もない。`framework/csrf/handlers.py`はcookieを配るが要求トークンを検証しない。`$osf.postJSON`を呼ぶだけではサーバ側の防御にならない。session cookieが送信される条件では他サイトの単純なformでも発行を誘発できる。ただし処理は状態を変更せず、部屋を作らずJSONを返すのみで、別のcross-origin露出がなければ同一生成元ポリシーが資格情報の読取りを防ぐ。資格情報窃取や状態変更CSRFは実証されていない。POSTならCSRF/Origin検証を明示するか、読取専用GETとno-storeの設計を説明してclientも整合させることを推奨する。選んだmethod・origin・session cookieの動作を試験し、現状のPOSTをCSRF保護済みとは記載しないこと。

### 根拠と限界

全差分、routing/renderer、認証、project/database guard、privacy hookを読んだ。実viewと判定をAST抽出しモデルをstubにした9条件の試験が合格。登録への追加防御も含むが、framework統合試験ではない。追加された試験は編集者・匿名・非貢献者・読取専用・除名・公開編集・部屋なし・秘密なし・methodを扱うが、削除/登録ノードとcache/CSRFは扱わない。OSFのDB/runtimeは起動せず、作者報告のpytest 13件は独立再実行していない。frontendの実provider試験では更新callbackをstubにして応答契約を確認した。

変更対象は独自scratch、本レビュー記録、依頼されたPRコメント1件のみ。commit・push・merge・approve・Docker状態変更・runtime/.envへのアクセスは行っていない。
