Every read of `filelog` in both the ordinary file-action branch and the move/copy/rename branch follows an assignment in the same function call (`osf/models/mixins.py:120–142`). A search found no external consumer that depends on the removed module variable. Concurrent calls now retain their own FileLog objects, including the user, project, path and optional date.

The two new tests in `osf_tests/test_loggable_filelog_concurrency.py` check the actual method's local-variable binding and force the previously failing order: A creates a FileLog, B creates and saves its FileLog, then A resumes. The date object's truth test provides synchronization after assignment, and the expected saved records distinguish both users, projects, paths and dates. The test deliberately substitutes recorders for persistence and logging; it proves object isolation, not a database-backed concurrent HTTP transaction. Local execution passed both tests on the corrected method and rejected the old method in both tests. The move/copy/rename branch is covered by inspection of the same local binding, not by the new two-thread test.

**R1-02 — P3: resolved.** Commit `48405dda36` removes the elapsed-time measurement and one-second assertion. The threaded case requires the second client to receive `ok` within a 30-second socket timeout while the first connection remains open (`tests/test_dev_server_tasks.py:56–91`). The unthreaded control still waits three seconds without receiving a response. Cleanup closes the first connection before server shutdown. These checks preserve the functional distinction without a separate runner-speed requirement.

**BrandFactory CI fixture error: corrected.** Commit `e25c636ac0` changes only the generated name to `factory.LazyFunction(lambda: fake.company()[:30])` (`osf_tests/factories.py:1173`). This matches `Brand.name`'s 30-character limit (`osf/models/brand.py:17`), leaves explicit factory overrides available, and does not change production model behavior. The existing module-level Faker instance is already used by other factories. This local check did not instantiate a database-backed Brand; the CI results supply repository-level validation.

<a id="followups-en"></a>
### Whether the additional shared state blocks PR #15

**Wiki `can_start_import`: separate follow-up; no new P1/P2 for this PR.** `addons/wiki/views.py:828–855` resets and returns a module-global boolean, and `:909–930` mutates it during validation. It is a real candidate for per-task state isolation if multiple validations run concurrently inside one process. The checked production-code caller of `project_wiki_validate_for_import_process()` is `addons/wiki/tasks.py:20–22`; the web view queues that task with `.delay()` at `addons/wiki/views.py:820`. The route is in the Flask wiki route table, and the PR changes Django API/admin runserver commands. The checked default Celery configuration does not enable eager execution or a thread pool, and the worker invocation does not select a thread pool. The explicit eager override is in tests. Removing `--nothreading` therefore does not move these validations into concurrent API/admin request threads. A follow-up should replace the global with state returned through the validation call chain and test concurrent validations. This conclusion covers tracked/default configuration; it does not assert safety for a custom eager/threaded Celery deployment.

**CORS whitelist append: separate follow-up; no new P1/P2 for this PR.** `api/base/middleware.py:112` concatenates `api_settings.ORIGINS_WHITELIST` onto `settings.CORS_ORIGIN_WHITELIST` on every applicable origin check. Both are tuples in the checked configuration. The origins snapshot is loaded by `api/base/wsgi.py:61`, from `api/base/settings/__init__.py:48–56`; no request-path refresh or origin-specific append was found. Concurrent read/concatenate/assign operations can overwrite another append, but each appends the same snapshot and preserves the initial allowed origins. Thus the distinct allowed-origin set does not change with that interleaving; duplicate counts can change. Repeated tuple growth when the snapshot is nonempty is a pre-existing memory/copy-cost defect, also present with serial requests. It should be fixed separately by avoiding per-request mutation, with repeated and concurrent CORS tests. This finding is not a general endorsement of other CORS policy behavior.

Neither follow-up issue was created during this review: the authorized remote write is exactly one PR comment.

### 追加の共有状態が PR #15 を妨げるか

**Wiki の `can_start_import`: 別件対応でよく、今回の新たな P1/P2 にはしません。** `addons/wiki/views.py:828–855` はモジュール全体で共有する真偽値を初期化して返し、`:909–930` が検証中に変更します。同一プロセス内で複数の検証を同時実行する場合には、タスクごとに分離すべき実際の候補です。確認した本番コードで `project_wiki_validate_for_import_process()` を呼ぶのは `addons/wiki/tasks.py:20–22` で、Web view は `addons/wiki/views.py:820` の `.delay()` でタスクをキューに入れます。経路は Flask の Wiki ルート表にあり、この PR が変えるのは Django API/admin の runserver コマンドです。確認した既定の Celery 設定は eager 実行もスレッドプールも有効にせず、worker 起動もスレッドプールを選択しません。明示的な eager 設定はテストにあります。したがって `--nothreading` の削除で、この検証が API/admin の同時要求スレッドへ移るわけではありません。後続対応では、検証の呼出し間で結果として状態を返し、同時検証をテストするのが適切です。この判断は追跡された既定設定を対象とし、独自の eager／スレッド方式の Celery 配備の安全性を保証するものではありません。
