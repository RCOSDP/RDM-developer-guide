### PostgreSQL test validity

`addons/twofactor/tests/test_concurrency.py` uses two additional aliases pointing to the test database. Their writes commit outside the default alias's surrounding test transaction, and Django's thread-local connections give the worker a separate session. Thus these are real overlapping database operations, not mock lock assertions. The fixture row is created through an explicit alias and is visible to both sessions. Cleanup deletes it before dropping aliases; worker exceptions propagate through `_finish`.

The first scenario holds an uncommitted advance to 101 while a stale save waits; after commit, that save must retain 101 and persist confirmation. The reverse scenario holds a save's transaction while a conditional update waits, then requires one update and final counter 101. The routed cases patch `django.db.router.db_for_write`, the shared router object actually used by both the implementation and Django, rather than an unrelated substitute. They cover preservation and reset on a non-default alias. On the previous implementation, a non-default SELECT FOR UPDATE lacks the matching transaction and fails.

Connection startup sets `lock_timeout=15000`; lock observation and join each have a 10-second bound. This prevents an indefinitely blocked PostgreSQL lock acquisition. The test requires PostgreSQL with `pg_stat_activity.wait_event_type` available. A minor test-strength limitation remains: wait detection counts any lock waiter in the current database rather than identifying the worker PID. Concurrent unrelated lock waiters could weaken proof of the intended overlap. On an isolated test database the scenarios are appropriate, and their final state assertions remain meaningful. This is not a production regression or a blocking finding. No claim is made that lock_timeout bounds every possible network or query delay.

### GitLab bytes and route coverage

`addons/gitlab/utils.py:39` preserves bytes unchanged and UTF-8 encodes text. HMAC therefore uses the actual Flask request body instead of raising `AttributeError`. The existing constant-time helper still receives the signature and digest. The application test configuration propagates that error, so expecting the exception is appropriate; temporarily disabling preserved exception context avoids leaking the failed request context. The valid route test would fail at the previous bytes `.encode()` call, and the forged route test would raise the wrong exception there. The added utility test separately covers bytes compatibility. No new regression was found in these changes.

### TOTP 保存の DB 振り分け

`addons/twofactor/models.py:133–145` は `using` を一度決める。明示キーワードを優先し、それ以外はインスタンスをヒントとして Django の共有 router を呼ぶ。同じ alias を `transaction.atomic`、`select_for_update` の queryset、親クラスの保存に渡す。queryset の評価と親クラスの保存完了は同じ atomic ブロック内にあり、書き込み中の行ロックを維持する。秘密値不変時の最大カウンタ維持と秘密値変更時のリセットは保たれる。新規作成とカウンタを含まない部分保存は従来どおりロックを省く。

独立検証では head の実メソッドを最小 Django モデルへ抽出し、default と primary の独立 SQLite DB を使用した。router 経由と明示 primary の双方で、古いオブジェクトの 50 が保存済み 100 を下げないことを確認した。ロック query はすべて primary の transaction 内で評価され、その間 default は transaction 外だった。保存行は primary だけに存在した。秘密値リセット後のカウンタは null を維持した。Django の SELECT FOR UPDATE transaction 検査を有効にし、SQLite 非対応の SQL 末尾だけを省いた。alias 伝播と transaction 構造の検証であり、実 PostgreSQL ロックの検証ではない。

### PostgreSQL 試験の妥当性

`addons/twofactor/tests/test_concurrency.py` は試験 DB を指す追加 alias 二つを使う。それらの書き込みは default の試験用 transaction の外で commit され、Django のスレッドごとの接続により worker は別セッションになる。mock によるロックの断言ではなく、実 DB 操作を重ねる設計である。試験行は明示 alias で作成され、両セッションから見える。後片付けは alias 削除前に行を消し、worker の例外は `_finish` から伝播する。

第一のシナリオは未 commit の 101 への更新を保持して古い保存を待たせる。commit 後の保存は 101 を維持し、確認済み状態も保存しなければならない。逆順のシナリオは保存の transaction を保持して条件付き更新を待たせ、更新件数 1 と最終値 101 を要求する。振り分け試験は `django.db.router.db_for_write` を patch する。実装と Django が使う共有 router そのものであり、無関係な代替物ではない。default 以外での維持とリセットを確認する。旧実装では別 alias の SELECT FOR UPDATE に対応する transaction がなく失敗する。

接続開始時に `lock_timeout=15000` を設定し、待機観測と join はそれぞれ 10 秒を上限とする。PostgreSQL のロック取得が無期限に待ち続けることを防ぐ。`pg_stat_activity.wait_event_type` を利用できる PostgreSQL が必要である。小さな試験上の限界として、待機検出は worker の PID ではなく、現在の DB の全ロック待機を数える。無関係な待機が同時発生すると、意図した重なりの証明が弱くなる。隔離した試験 DB では妥当なシナリオで、最終状態の検査も有効である。製品の退行でも阻害指摘でもない。lock_timeout がすべての通信・query 遅延を制限するとは主張しない。

### GitLab bytes とルート試験

`addons/gitlab/utils.py:39` は bytes をそのまま保ち、text を UTF-8 に encode する。HMAC は `AttributeError` を起こさず、Flask の実要求本文を使う。署名と digest は既存の定数時間ヘルパーへ渡される。実検証関数とヘルパーの独立実行では、bytes・text・UTF-8・空本文と、正しい署名・偽造・欠落・非 ASCII 署名の組み合わせ 24 件が成功した。`hmac.compare_digest` に到達することも確認した。

`addons/gitlab/tests/test_views.py:344–380` の新試験は encode 済み JSON を実 webhook URL に送る。署名検証関数と定数時間ヘルパーは mock していない。後続のログ書き込みだけを mock にし、正しい本文署名では HTTP 200 とログ一回、偽造署名では `HookError` とログ零回を要求する。試験アプリは例外を伝播するため例外を期待するのは妥当で、例外時の context 保持を一時的に無効にすることで失敗要求の context を残さない。旧実装では正しい署名のルート試験は bytes の `.encode()` で失敗し、偽造署名の試験は違う例外で失敗する。追加の単体試験も bytes の互換性を確認する。今回の変更に新しい退行は見つからなかった。
