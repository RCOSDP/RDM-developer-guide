### R6-01 — P2, closed: do not reuse a populated QuerySet cache

**Affected intermediate location:** `api_tests/base/test_session_expiry_http.py:84,90` at `beb16c84ed`. **Resolution:** lines 84–93 at `f991bc2720`, unchanged through reviewed head `71e26d2751`.

The intermediate code calls `list(owner_sessions)` and later asserts `not owner_sessions.exists()`. The first call fills the QuerySet's result cache. Django 1.11.28, pinned at `requirements.txt:66` in that intermediate revision, returns the cache's truth value from `exists()` when it has been populated. Deleting individual model objects does not clear that QuerySet cache. The assertion therefore fails even when the database contains no matching rows.

The author's extracted proof uses a fake QuerySet whose `exists()` always checks current rows, so it cannot detect this defect. The independent probe uses the actual Django 1.11.28 `__iter__`, `__len__`, `_fetch_all`, and `exists` method bodies, together with the unmodified fixture cleanup extracted from each revision. It reproduces 15 teardown assertion failures among 18 simulated cases on the intermediate revision; the two `deleted` cases and the single `missing_user` case have an empty owner-query cache. The repaired code checks fresh QuerySets and has zero such failures under both Django 1.11.28 and 2.2.28 method bodies. R6-01 is historical evidence, not an open request against the final head.

### R6-03 — P1, closed in efee5aa47e: legacy public wiki flags bypass private authorization

Even when the node's canonical `can_view` and `can_edit` both refuse that outsider, `_can_edit_wiki` accepts the editable flag and the renewal endpoint mints a room token. The write decorator likewise invokes the edit body without checking WRITE. API v2's page and version permissions accept the public flag for reads even when public editing is disabled, and its page permission accepts the editable flag for writes. `WikiMixin.get_wiki` loads the page by ID and applies those object permissions; it adds no independent parent-read check. Anonymous authentication rejection alone therefore does not close the authenticated outsider's access.

The exact extracted method bodies reproduce token-minting, entry into the decorated write body, and permission grants for page GET/POST and version GET with no READ/WRITE permission. Removing the stored public flags makes all those controls deny access. Evidence: `wiki-private-probe.py` and `wiki-private-probe.json`. It exposes wiki contents and permits editing or collaborative-session access to unrelated authenticated accounts. Restrict public/editable exceptions to `ENABLE_PUBLIC_ACCESS=true`; in private mode use the canonical node visibility/editing and WRITE checks. Add real-request regression cases for legacy-public data across anonymous, outsider, READ, and WRITE users, including wiki renewal/edit and API page/version content. Preserve the intended public-mode behavior. Do not defer this as a separate-PR limitation while reporting pass.

### R6-05 — P2, open: permission-aware child counts still trust stored public flags

**Location at `71e26d2751`:** `api/nodes/serializers.py:715` in `NodeSerializer.get_node_count`; the same SQL also retains an unconditional view-only-link branch at line 728.

A logged-in user with READ on a parent but no access to its child can request `GET /v2/nodes/<parent>/?related_counts=children`. The child's legacy `is_public=true` alone includes it in `data.relationships.children.links.related.meta.count`, even with `ENABLE_PUBLIC_ACCESS=false`. Clearing only the child's stored flag removes it from the count. The ordinary children endpoint filters through `can_view` and does not include this child in private mode. This exposes the number of inaccessible formerly public children and makes the API's count disagree with its authorized list. The method expressly promises a count of children the user may view; existing public-mode tests also require count/list agreement. This is not merely displaying a flag on an already authorized object, so classification A in AID comment 6809886943 is incorrect for this occurrence.

Evidence: `children-count-probe.py` executes the SQL extracted from the actual method against an in-memory SQLite database, adapting only placeholders and PostgreSQL's implicit EXISTS column names. With parent-only READ, it returns 1 for an inaccessible legacy-public child, 0 after clearing its public flag, and 1 after granting explicit child READ. A private-link-only child likewise counts as 1. The source contains no instance-setting check. `children-count-probe.json` records those results. This validates the query logic; no real HTTP or PostgreSQL reproduction is claimed. The API wiring is `api/nodes/serializers.py:372–375`, `api/base/serializers.py:670–687`; the authorized list is `api/base/views.py:491–503` and `osf/models/node.py:151–167`; existing count/list expectations are in `api_tests/nodes/views/test_node_detail.py:396–452`.

**Required correction:** In private mode, count exactly the non-deleted direct children that the canonical visibility query allows, ignoring both legacy public flags and view-only links. Retain explicit READ, OSF/Mapcore group and inherited parent ADMIN access, with no duplicate counts. Add actual-request regressions comparing `related_counts=children` to the children list for a parent reader, an authorized child reader, parent administrators and groups, plus private/public mode controls. The new `tests/test_private_public_flag_boundaries.py` does not exercise this query. R6-05 prevents a pass independently of CI.
