### Required changes

**R2-01 / P1 — complete the paired server expiry boundary.** In the paired PR #5, `bin/server.cjs:52–55` sends 4401 but keeps the message listener in `bin/utils.cjs:348`. An adversarial client can withhold its close reply and send a Yjs update after receiving 4401. A real loopback server and two clients independently reproduced the other client's text becoming `AFTER-EXPIRY`. The server must revoke document/awareness access immediately and reject frames during closing, with a regression test. R1-02 cannot be closed by a browser-only expiry/downgrade test. See the companion record, R1-01.

**R2-02 / P2 — separate stale-room cleanup from permission to renew.** `addons/base/views.py:1159–1176,1219–1224` leaves the old mapping in place if DELETE fails, then accepts every retained mapping for renewal. After a timeout or HTTP 500 while viewing the new version, a still-authorized writer can keep receiving fresh tokens for the superseded room indefinitely if nobody revisits the new version. The deletion-retry test even preserves both mappings. An isolated probe executing the three actual function bodies with mocked external dependencies returned a fresh old-room token after deletion failure. Reject superseded versions independently of remote cleanup, and retain a separate retry record; test failure followed by renewal 404. Cleanup currently runs on a later editable page view, not on the file-version save itself, so the claimed save-time deletion also needs an explicit lifecycle decision.

### Persistence decision and security boundary

The proposed policy is file-prefix-only LevelDB persistence, 4 MiB per encoded room and 256 MiB overall, with overflow reverting to memory-only operation. This deliberately permits loss of an unsaved draft when its last client leaves after overflow. The proposed deletion policy closes peers with 4410 and uses in-memory tombstones. Those tombstones disappear on restart. These are design decisions, not verified deployment settings or proof of stakeholder acceptance.

The server's bounds and deletion race fail independent probes (companion R1-02/R1-03). `Y_WEBSOCKET_INTERNAL_URL` defaults to empty; `addons/wiki/utils.py:101–104` then reports deletion success and forgets the mapping without deleting disk data. A deployment enabling persistence must set a reachable internal URL as well as a durable LevelDB directory and the `file-` prefix. No runtime configuration or Docker stack was inspected or changed.

The delete credential is minted only in the server-side helper, carries `purpose: delete`, exact `doc_id`, and a 60-second expiry. Normal room credentials cannot call the deletion API. The HTTP endpoint itself is not restricted by source address; refer to the server record.

### 必要な修正

**R2-01 / P1 — 対応サーバーの期限切断を完成させる。** 対応PR #5 の `bin/server.cjs:52–55` は4401を送るが、`bin/utils.cjs:348` のメッセージ受信は残る。改造クライアントが切断応答を返さず、4401受信後にYjs更新を送ると、別クライアントの本文が `AFTER-EXPIRY` になることを実サーバーと2クライアントで独立再現した。文書・awarenessへのアクセスを即座に失効させ、切断中のフレームを拒否する回帰試験が必要。通常ブラウザの期限・降格試験だけではR1-02を解消できない。対応サーバー記録のR1-01を参照。

**R2-02 / P2 — 旧部屋の掃除とトークン更新の認可を分ける。** `addons/base/views.py:1159–1176,1219–1224` はDELETE失敗時に旧対応表を残し、その全項目を更新時に許可する。新版表示中のタイムアウトやHTTP 500の後、新版を誰も再表示しなければ、WRITEを持つ利用者は置換済みの部屋のトークンを繰り返し更新できる。削除再試行の試験も新旧両方の対応を残している。実際の3関数の本体を外部依存の代役で実行した独立試験でも、削除失敗後に旧部屋の新規トークンが返った。遠隔削除の成否と独立に旧版を拒否し、再試行記録を別管理し、失敗後の更新404を試験する必要がある。掃除の契機は版保存自体ではなく後続の編集可能なページ表示なので、保存時削除という説明についてもライフサイクルを明確にする必要がある。

### 永続化の判断と安全性の境界

提案は、ファイル接頭辞だけのLevelDB永続化、部屋の符号化状態4 MiB、全体256 MiB、超過時はメモリのみへ切り替える方針。超過後に最後の接続が離れると未保存下書きが失われることを許容する設計となる。削除は4410とメモリ上の削除済み記録を使い、この記録は再起動で消える。これらは設計方針であり、配備設定や関係者の受容を検証したものではない。

対応サーバーの上限と削除競合は独立試験で問題が出た（対応記録R1-02/R1-03）。`Y_WEBSOCKET_INTERNAL_URL` の既定は空で、`addons/wiki/utils.py:101–104` はその場合にディスク削除なしで成功扱いして対応表を忘れる。永続化を有効にする配備では、到達可能な内部URL、永続的なLevelDBの場所、`file-` 接頭辞を設定する必要がある。runtime設定とDockerスタックにはアクセスも変更もしていない。

削除用資格情報はサーバー側のヘルパーだけで発行し、`purpose: delete`、正確な `doc_id`、60秒の期限を持つ。通常の部屋用資格情報では削除できない。ただしHTTPエンドポイント自体には接続元アドレスの制限がない。詳細はサーバー記録を参照。
