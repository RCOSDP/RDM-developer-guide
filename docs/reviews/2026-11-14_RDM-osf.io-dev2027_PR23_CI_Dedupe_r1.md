### P2 — Pending branch pushes and weekly scans are not preserved

Locations: `.github/workflows/codeql.yml:11-13` and `.github/workflows/unit-tests.yml:13-14`, plus the PR description's promise that main/develop pushes and weekly CodeQL are not canceled.

A concurrency group limits work sharing the same key. The expression in `cancel-in-progress` is valid and protects a running non-PR workflow. It does not protect an already pending workflow. With the default queue behavior, a newer pending run replaces the previous pending run even when `cancel-in-progress` is false. This follows the [GitHub concurrency documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).

The repository's default branch is `develop`. A weekly CodeQL run and a push to develop both use `codeql-refs/heads/develop`. If push A is running, the weekly scan waits, and push B arrives, B can cancel the waiting weekly scan. The reverse replacement is also possible. Three pushes to the same branch can likewise discard the middle pending Unit Tests or CodeQL run. Merely adding the event name separates schedule from push but does not preserve every pending push.

This matters because the PR explicitly promises not to cancel these runs. Deduplicating superseded PR revisions is intended; silently discarding a weekly scan or an intermediate merged-branch revision is a different policy. Preserve non-PR runs with unique, separately prefixed run identities while retaining stable PR groups, or explicitly agree to and document the reduced coverage. The former matches the current PR promise. No workflow was triggered, canceled, or rerun to demonstrate this scenario; it is a deterministic consequence of the documented grouping rules.

The removal of tests for branches without a PR is already disclosed and is reasonable for the stated PR-centered workflow.

### P2 — 待機中のブランチpushと週次スキャンが保護されない

箇所: `.github/workflows/codeql.yml:11-13`、`.github/workflows/unit-tests.yml:13-14`、およびmain/developへのpushと週次CodeQLを取り消さないとするPR本文。

concurrency groupは同じキーの処理を制限する仕組みである。`cancel-in-progress`の式は有効で、実行中の非PRワークフローを保護する。しかし、すでに待機中のワークフローは保護しない。既定のキュー動作では、`cancel-in-progress`がfalseでも、新しい待機実行が以前の待機実行を置き換える。[GitHubの同時実行制御の仕様](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)に基づく。

既定ブランチは`develop`である。週次CodeQLとdevelopへのpushは、どちらも`codeql-refs/heads/develop`を使う。push Aが実行中に週次スキャンが待機し、push Bが来ると、Bが待機中の週次スキャンを取り消し得る。逆の置き換えも起こり得る。同じブランチへのpushが3本続けば、Unit TestsでもCodeQLでも、間の待機実行が失われ得る。イベント名を加えるだけではscheduleとpushは分離できるが、すべての待機pushは保護できない。

PRはこれらを取り消さないと明記しているため、修正が必要である。更新前のPR実行を減らす意図と、週次スキャンや統合先ブランチの途中リビジョンを試験しない方針は異なる。PRには固定グループを残し、非PRには別の接頭辞と実行ごとの一意なキーを使って保護するか、減る検査範囲を明記して合意する必要がある。現在の説明に一致するのは前者である。再現のためのワークフロー起動・取り消し・再実行はしておらず、指摘は公開仕様とキーから導かれる。

### P3 — PRを開く案内に対象ブランチを明記する

影響欄は試験を回すにはPRを開くよう案内しているが、維持されるpull_requestフィルタは`main`または`develop`宛てだけを受け付ける。他のブランチ宛てにPRがあるfeatureブランチも、従来のpush試験を失う。影響欄にPRの宛先条件を記載してほしい。PRがないブランチの試験を省くことはすでに明記され、PR中心の運用として妥当である。

### 問題を認めなかった確認事項

Git差分全体は指定の2ファイルだけを変更する。各ファイルの`permissions: {}`から末尾まではbaseとheadでバイト単位で同一だった。`private_security`を含む6分割の試験、ジョブ本文、依存関係、制限時間、固定されたActionの版、権限は不変である。6という数は試験matrixを指し、別のbuild-imageジョブも残る。

main/developへのpushと、それらを宛先とするPRの起動条件は維持される。現在のブランチ一覧にはdevelopがあり、mainはない。mainの検査維持は設定上の確認で、実行を観測したわけではない。PRのキーは数値、ブランチのキーは`refs/heads/`付きなので衝突しない。Unit TestsとCodeQLの接頭辞は別で、異なるPR番号も分離される。問題となるイベント間の衝突はdevelopでのCodeQL scheduleとpushである。

developの保護設定の応答には必須ステータスチェックがない。リポジトリのrulesetとdevelopへの適用ルールも空だった。したがって、現在pushだけが提供する必須チェックは見つからなかった。mainの保護設定取得はbranch-not-foundとなり、ブランチ一覧と一致した。チェック名は変わらない。

権限追加、`pull_request_target`、新たな秘密情報の利用、トークン権限の拡大はない。fork PRも従来のpull_requestの安全性モデルを維持する。変更部分の結論であり、既存の全権限を改めて監査したものではない。

直近の実行履歴でも、以前の同じheadにpushとpull_requestのUnit Testsが重複し、約1〜2時間かかったことを確認した。本文は2ファイル、matrix不変、重複実行の動機、PRがないブランチへのpush検査廃止を正しく説明する。YAMLの読み取り検証は著者の報告であり、レビュワは差分とGitHubが定義を受理して実行した事実を独立に確認した。古いPR実行の自動取り消しは単一headでは実証できず、本文は適切に追加push時の検証としている。実行枠が1本という説明と過去の所有者判断は著者提供の背景であり、アカウント設定として独立に確認した情報ではない。
