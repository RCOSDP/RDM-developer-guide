### R1-01 resolved — Groups distinguish PRs from individual runs

Both workflow files now use the following group suffix, after their different workflow-name prefixes:

```yaml
${{ github.event_name == 'pull_request' && format('pr-{0}', github.event.pull_request.number) || format('run-{0}', github.run_id) }}
```

For pull_request, the first comparison is true and formatting PR number 23 produces the nonempty string `pr-23`. That string is truthy, so the OR expression returns it without taking the fallback. The important truthiness condition is the formatted string, not merely the numeric PR number. For push or schedule, the first comparison is false; the AND expression short-circuits before reading the PR number, and OR selects `run-<run_id>`. This uses valid single-quoted format strings and allowed github context values. The unchanged cancellation expression is true only for pull_request.

GitHub documents the [expression operators and format function](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions). The public Actions runner implementation corroborates short-circuit evaluation and returning operand values in its [AND operator](https://github.com/actions/runner/blob/8cfa1049f86781d141056082d73802d56cd2b433/src/Sdk/DTExpressions2/Expressions2/Sdk/Operators/And.cs) and [OR operator](https://github.com/actions/runner/blob/8cfa1049f86781d141056082d73802d56cd2b433/src/Sdk/DTExpressions2/Expressions2/Sdk/Operators/Or.cs). GitHub accepted both revised workflow definitions and started their runs.

The `pr-` and `run-` prefixes prevent a numeric PR identifier from colliding with a run identifier. Different PR numbers remain separate. The `unit-tests-` and `codeql-` prefixes separate the workflows. No other concurrency group declaration occurs in the reviewed workflow directory.

GitHub defines [github.run_id](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context) as unique for each workflow run in a repository. Therefore distinct develop/main pushes, and a weekly CodeQL schedule versus a push on develop, use different groups. They cannot replace each other's pending runs through this configuration. The identifier remains the same for a rerun attempt of the same run; uniqueness here means distinct workflow runs, not attempts. No rerun was requested or used in this review.

The YAML comments now accurately explain both the stable PR group and why non-PR runs need separate groups even with cancel-in-progress disabled. Their preservation claim concerns this concurrency mechanism, not manual cancellation, service failures, or unrelated platform limits. Same-PR superseded runs still share a group and are configured for cancellation. The [concurrency rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) no longer imply the r1 pending-run loss for distinct non-PR runs.

### R1-01解決 — PRと個々の実行を別グループにする

両ワークフローは、それぞれ異なるワークフロー名の接頭辞の後ろに、次のgroup接尾辞を使う。

```yaml
${{ github.event_name == 'pull_request' && format('pr-{0}', github.event.pull_request.number) || format('run-{0}', github.run_id) }}
```

pull_requestでは最初の比較がtrueとなり、PR番号23を整形すると空でない文字列`pr-23`になる。この文字列がtruthy（条件で真として扱う値）なので、OR式は代替値を選ばずその文字列を返す。重要なのは数値のPR番号だけでなく、整形後の文字列がtruthyになることである。pushとscheduleでは最初の比較がfalseとなり、AND式はPR番号を読む前に短絡評価し、OR式が`run-<run_id>`を選ぶ。書式文字列の単一引用符とgithubコンテキストの利用も有効である。不変の取り消し条件はpull_requestのときだけtrueになる。

GitHubは[式の演算子とformat関数](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions)を文書化している。公開Actions runner実装の[AND演算子](https://github.com/actions/runner/blob/8cfa1049f86781d141056082d73802d56cd2b433/src/Sdk/DTExpressions2/Expressions2/Sdk/Operators/And.cs)と[OR演算子](https://github.com/actions/runner/blob/8cfa1049f86781d141056082d73802d56cd2b433/src/Sdk/DTExpressions2/Expressions2/Sdk/Operators/Or.cs)でも、短絡評価と被演算子の値を返す動作を確認した。GitHubは修正後の両定義を受理し、実行を開始した。

`pr-`と`run-`の接頭辞により、数値のPR番号と実行IDは衝突しない。異なるPR番号も分離される。`unit-tests-`と`codeql-`によりワークフロー間も分離される。対象のワークフローディレクトリには、ほかの同時実行グループ定義はない。

GitHubは[github.run_id](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context)を、リポジトリ内のワークフロー実行ごとに一意と定義する。したがってdevelop/mainへの別々のpushや、develop上のpushと週次CodeQLは別グループになる。この設定によって互いの待機実行を置き換えることはない。同じrunを再実行する試行ではIDは変わらないため、一意性は試行ごとではなく別々のワークフロー実行についての説明である。本レビューで再実行は依頼・利用していない。

YAMLコメントは、PRには固定グループを使い、cancel-in-progressを無効にしても非PRには別グループが必要な理由を正しく説明する。保護の説明はこの同時実行制御についてであり、手動取り消し・サービス障害・別のプラットフォーム上限まで排除するものではない。同じPRの古い実行は引き続き同じグループに入り、取り消す設定である。[同時実行制御の規則](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)からr1で導かれた、別々の非PR実行の待機中取り消しは解消した。

### R1-02解決 — 本文が検査範囲と証拠の限界を明記する

影響欄はdevelopまたはmain宛てのPRが必要と明記し、ほかのブランチ宛てのPRだけではUnit Testsが走らないと説明する。文脈上は作業ブランチについての説明であり、変更欄にあるとおりmain/developへのpushは維持される。どの宛先でもPRを開けばよいという以前の案内は修正された。

本文は最初のheadの9件成功をr1の証拠として区別する。また、r2のpushはそれらの完了後なので、実行中の古いPR runの取り消しは未観測だと正しく記す。非PR実行の保護も、pushを重ねる実験ではなくgroup値とGitHubの仕様による判断としている。レビュワも、古いrunの完了が新しいrunの作成より前だったことを独立に確認した。重複runを除いたことから総所要時間の短縮までは推論しない。実行枠数の説明と過去の所有者判断は著者提供の背景であり、アカウント設定を独立に監査した情報ではない。

### 変更範囲は限定されたままである

baseからr2までの差分全体も、`.github/workflows/unit-tests.yml`と`.github/workflows/codeql.yml`だけである。r1からr2の差分は2つのgroup式と説明コメントだけだった。起動条件、cancel-in-progress式、権限は不変であり、各ファイルの`permissions: {}`から末尾まではr1とバイト単位で同一である。別のbuild-imageジョブと、private_securityを含む6分割の試験はすべて残る。

権限、pull_request_target、Actionの版、秘密情報アクセス、トークン権限の拡大はない。fork PRの安全性モデルも変わらない。限定された差分はr1で確認した保護設定・起動条件の結論を覆さないが、r2でリポジトリ管理設定を再監査したとは主張しない。
