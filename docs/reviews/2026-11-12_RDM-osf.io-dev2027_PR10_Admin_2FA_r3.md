### Mixed-process “connection already closed” diagnosis

The author's four failures are reproducible: the unmodified head's `admin_tests/common_auth admin_tests/base addons/twofactor/tests` run produced **212 passed, 4 failed**. All four failures are the Flask twofactor view tests. They fail in the authenticated-user lookup before the twofactor view body.

The trace identifies the lifecycle conflict. `tests/base.py:45–51` removes Flask's Django database callbacks so pytest's enclosing transaction remains usable. Loading the admin URL configuration imports `admin.rdm_addons.views`; its existing `init_app()` at lines 21–37 calls `attach_handlers()` again. The reattached `framework/django/handlers.py:9–21` calls `close_old_connections()` inside the test transaction. Django 2.2's `close_if_unusable_or_obsolete()` sees autocommit differ from the configured default and closes the connection. The next lookup fails with `InterfaceError`. The first closure is captured before the user lookup, with `in_atomic_block=True`, `autocommit=False`, and `closed_in_transaction=False`.

A reviewer-only fixture removes precisely those callbacks around the four affected tests and restores their prior registry afterward. With production code and assertions unchanged, the combined run becomes **216 passed**. This is diagnostic evidence, not a submitted fix. On develop `73ff43b3` with a separate database, a minimal admin-URL import test followed by the same four view tests produces **1 passed, 4 failed**. Deselecting that import test produces **4 passed, 1 deselected**. The callback-registration code is unchanged in the r3 delta.

The normal application registry does not undergo the test harness's callback removal; `framework/flask/__init__.py` adds a handler only when it is absent. This distinction explains why the demonstrated failure is tied to test initialization order.

**Assessment:** This is an inherited test-isolation defect, not evidence that PR #10 newly breaks the production TOTP path. CI's split hides a real test-isolation problem; separate green jobs alone were not an adequate explanation. Keep this as a test-harness follow-up with an import-order regression test. Do not “fix” production by disabling connection cleanup. No additional product P1/P2 is established by this failure once the lifecycle control and baseline evidence are considered.

### 同一プロセスの “connection already closed” の診断

作者の4失敗を再現した。未変更headの `admin_tests/common_auth admin_tests/base addons/twofactor/tests` は **212 passed、4 failed**。失敗は4つともFlask側のtwofactorビュー試験で、ビュー本体の前の認証利用者取得時に発生する。

レビュワ専用fixtureで4試験の間だけ該当callbackを外し、終了時に元の登録内容を復元すると、製品コード・assertionを変えずに混合試験は **216 passed** となる。これは診断用の対照試験であり、提出した修正ではない。develop `73ff43b3` の独立したDBでも、管理画面URL設定をimportする1試験の後に同じ4ビュー試験を実行すると **1 passed、4 failed**。import試験を除外すると **4 passed、1 deselected** となった。原因のhandler登録コードはr3差分で変更されていない。

通常のアプリでは試験基盤によるcallbackの除去はなく、`framework/flask/__init__.py` は未登録のhandlerだけを追加する。この違いが、再現した失敗が試験初期化順序に依存する理由である。

**評価:** これは既存の試験分離の不具合であり、PR #10 が新たにTOTPの実行経路を壊した証拠ではない。 CI の分割は実在する試験分離の問題を隠すので、「別実行で成功する」だけでは説明不足だった。import順序の回帰試験を伴うテスト基盤の後続課題として扱う。本番の接続cleanupを無効にする修正はしない。接続ライフサイクルの対照試験とdevelop基準の証拠を踏まえ、この失敗から追加の製品P1/P2は認定しない。
