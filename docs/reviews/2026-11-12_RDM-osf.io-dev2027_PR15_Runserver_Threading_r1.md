<a id="findings-en"></a>
### Findings

**R1-01 — P2: make the file audit-log variable request-local before enabling concurrent API requests.** The changed command at `tasks/__init__.py:157` enables concurrent execution of code that still declares `global filelog` in `osf/models/mixins.py:99`. `Loggable.add_log()` assigns a new `FileLog` at lines 119–122 and then reads the global again at lines 123–125; the move/copy/rename branch repeats the pattern at lines 135–141. A second request can replace that object between assignment and save. The first request can consequently save the other user's/project's file log, leaving its own file audit record absent; a supplied log date can also be applied to the wrong object.

This is reachable from development API requests: `api/files/serializers.py:330–337` calls file tag mutation or `check_in_or_out()`, and `addons/osfstorage/models.py:228` and `:426` call `target.add_log()`. Although the global declaration predates the PR, the development API previously serialized these calls through `--nothreading`; enabling threads exposes the latent race in this execution path. Database transactions and the middleware's thread-local request pointer do not isolate a Python module global.

A deterministic two-thread harness executed the actual `add_log()` method extracted from the reviewed source, with model persistence replaced by recording doubles. It paused request A at line 123 after assignment, allowed request B to finish, and resumed A. The saved records were `(B, user-B, /B, project-B)` and `(A, user-B, /B, project-B)`, where the first item names the executing request. A control that removed only the `global` declaration from the extracted method produced `(B, user-B, /B, project-B)` and `(A, user-A, /A, project-A)`. This establishes the reference-sharing defect; it is not a claim that a full database-backed HTTP test was run.

**Requested correction:** remove `global filelog` so the existing assignments use a function-local variable, and add a coordinated two-request/thread regression test that verifies distinct users, projects, paths and log dates remain attached to their own records. Retain the development threading fix after that correction.

**R1-02 — P3: avoid the extra one-second performance threshold in the functional regression test.** `tests/test_dev_server_tasks.py:84–86` requires the second response to arrive in less than one second, even though the client allows three seconds. A healthy threaded server can fail that assertion if its test process is descheduled for more than a second. Neither local verification nor the two successful CI website jobs exhibited a timing failure. Prefer asserting that the response completes while the first connection is still open, using a generous bounded timeout; this checks the intended behavior without treating runner speed as correctness.

### 指摘

**R1-01 — P2: API の同時要求を有効にする前に、ファイル監査ログの変数を要求ごとに分離してください。** `tasks/__init__.py:157` の変更により、`osf/models/mixins.py:99` で `global filelog` を宣言したままの処理が同時に実行されます。`Loggable.add_log()` は 119〜122 行で新しい `FileLog` を代入し、123〜125 行でその共有変数を再び参照します。移動・コピー・名前変更の分岐の 135〜141 行も同じ構造です。代入から保存までの間に別の要求がオブジェクトを置き換えると、先の要求は別ユーザー・別プロジェクトのログを保存し、自分のファイル監査記録を失う可能性があります。日時が指定された場合、その日時も誤ったオブジェクトに適用され得ます。

開発 API から到達する経路があります。`api/files/serializers.py:330–337` はファイルタグ操作または `check_in_or_out()` を呼び、`addons/osfstorage/models.py:228` と `:426` は `target.add_log()` を呼びます。共有変数の宣言自体は既存ですが、開発 API では従来 `--nothreading` によってこの処理が直列化されていました。スレッド化により、この経路で潜在的な競合が表面化します。データベースのトランザクションやミドルウェアのスレッド別要求ポインターでは、Python モジュールの共有変数を分離できません。

確認対象のソースから実際の `add_log()` を抽出し、モデルの保存部分だけを記録用の代役に置き換えた、実行順序を固定する二スレッドの検証を行いました。代入後の 123 行で要求 A を止め、要求 B を完了させてから A を再開しました。記録は `(B, user-B, /B, project-B)` と `(A, user-B, /B, project-B)` になりました。先頭は実行中の要求です。抽出したメソッドから `global` 宣言だけを除いた対照実験では、`(B, user-B, /B, project-B)` と `(A, user-A, /A, project-A)` になりました。これは参照共有の欠陥を示しますが、実データベースを使う HTTP 統合テストを実施したという意味ではありません。

**修正依頼:** `global filelog` を削除し、既存の代入先を関数内のローカル変数にしてください。実行順序を制御する二要求・二スレッドの回帰テストを追加し、各記録のユーザー、プロジェクト、パス、日時が混ざらないことを確認してください。その修正後も開発サーバのスレッド化は維持してください。

**R1-02 — P3: 機能回帰テストの追加の一秒性能条件を避けてください。** `tests/test_dev_server_tasks.py:84–86` は、クライアント側が三秒待てる設定でも、一秒未満での応答を要求します。テストプロセスに一秒以上 CPU が割り当てられなければ、正常なスレッド方式でも失敗し得ます。ローカル検証と、成功した二つの CI website ジョブでは、タイミング失敗は観測されませんでした。余裕のある上限時間を使い、一つ目の接続が開いている間に二つ目が応答することを確認すれば、実行環境の速さを正しさの条件にせず目的を検証できます。
