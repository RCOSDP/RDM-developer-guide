### Verdict and scope

**Changes requested.** R4-01 and the N1 recommendation are closed. R5-01 remains: the fixture (the setup and cleanup used by tests) removes the initial session but leaves a replacement session behind. This is an incomplete repair of pre-existing test-data leakage, not evidence of a new production authentication bypass.

The reviewed range contains one commit and three test files, with 25 added and 3 removed lines. No production or workflow file changed. Review used a separate scratch clone, GitHub reads, source inspection, and execution of extracted functions with simulated dependencies. No application HTTP, database, or Elasticsearch integration test was rerun. No Docker operation, runtime directory or environment-file access, commit, push, approval, merge, or close was performed.

### R5-01 — P2: delete renewal sessions during teardown

**Location:** `api_tests/base/test_session_expiry_http.py:77–82`.

The new loop deletes only the objects represented by `session`, `project`, and `owner`. Both HTTP test families call `owner.get_or_create_cookie()` in their `renewed` and `old_after_renewal` cases. At `osf/models/user.py:1972–1985`, that method finds the expired session and saves a **new** `Session`; it does not replace the fixture's `session` variable.

`osf/models/session.py:5–6` stores the user identifier in `data`, a JSON field (structured text), rather than a foreign key (a database link that can arrange related deletion). Deleting `owner` through `models.Model.delete` therefore does not delete the newly created session. The reviewed code has no user-deletion signal that supplies this cleanup. The new loop can remove the initial session, project, and user while leaving an orphan session containing the old user's identifier and name.

The probe executed the actual extracted `get_or_create_cookie` method and actual cleanup loop with an in-memory model stand-in. Fresh and already-deleted cases left no sessions; each renewal case left one. This is a source-backed reproduction of the cleanup logic, not a claim to have rerun the application's database stack. The author's statement that no new residual rows remain is not supported for these renewal rows.

Persistent rows undermine isolation in the shared test database. For example, `osf_tests/test_session.py:24–31` asserts the total session count after adding two sessions, so running it against such residual rows can make the result depend on test order. This does not claim that the current green CI run failed or used that order.

**Requested correction:** Before deleting the owner, delete every session whose `data__auth_user_id` equals the fixture owner's saved identifier. Retain deletion by the initial session's primary key as well: the `missing_user` case changes the identifier in its JSON. Keep the already-deleted-session tolerance and server shutdown before row deletion. Verify all 18 HTTP cases and assert after teardown that the original row, all renewal rows for that owner, the project, and the owner are absent. Include a following session-count check in the same database.

### Closed findings and regression checks

**R4-01:** `tests/nii/test_search_api2.py:216–226` follows the returned users link using the same caller's authentication and checks exact equality with `{user._id}`, plus explicit exclusion of both unrelated users. Parsing the link preserves its path and encoded query. Existing summary counts and other category/link assertions remain.

The actual extracted old and new test methods were run with simulated responses. The summary still reported one user in every case. The old method accepted all responses because it never requested the user list. The new method accepted the caller alone and rejected one unrelated user, the caller plus both unrelated users, and an empty list. This independently confirms that the assertion catches the R4-01 failure shape. The author's separate production-code mutation is recorded in the response to r4 (RDM-osf.io-dev2027 PR #8, comment 6795434539); it was not rerun here.

**N1:** Both `test_normalize_all` rebuild calls now pass `user_pattern=del_func is _del_user` at lines 764–767 and 780–783. The wrapper forwards keyword arguments in both its rebuild/retry and direct-execution paths. The outsider check therefore runs for the user patterns in both normalization directions, while the shared-user positive check remains. In `test_normalize_user_ongoing_job_school:1410–1426`, the reverse branch now checks the default outsider before checking shared user `user5`; it mirrors the existing forward branch and retains the six profile-field checks. These paths were inspected and their changed call structure checked with AST (Python's parsed source structure).

**Fixture improvements retained:** The UUID username avoids the factory's repeated random-email problem. The cleanup shuts down and joins all servers before deleting rows, and tolerates the original session already being deleted. The defect is the missing replacement sessions, not the unique username or shutdown order.

### R5-01 — P2: 更新後のセッションも後始末で削除する

**箇所:** `api_tests/base/test_session_expiry_http.py:77–82`。

新しいループが削除するのは、`session`・`project`・`owner` が指す行だけです。HTTP 試験の両系列にある `renewed` と `old_after_renewal` は `owner.get_or_create_cookie()` を呼びます。`osf/models/user.py:1972–1985` の実装は期限切れセッションを見つけると **新しい** `Session` を保存し、fixture の `session` 変数は更新しません。

`osf/models/session.py:5–6` の利用者識別子は JSON フィールド（構造を持つ文字データ）内にあり、外部キー（関連する行を一緒に削除できるデータベースの結び付け）ではありません。そのため `models.Model.delete` で `owner` を削除しても、新しいセッションは消えません。確認したコードには、その削除を補う利用者削除時の処理もありません。新しいループは初期セッション・プロジェクト・利用者を消しながら、削除した利用者の識別子と氏名を持つ孤立セッションを残します。

実際の `get_or_create_cookie` メソッドと後始末ループを抽出し、メモリ上のモデル代用品で実行しました。fresh と削除済みの場合は残留なし、更新の各ケースでは 1 行残りました。これはソースに基づく後始末ロジックの再現であり、アプリの実データベースで再実行したという意味ではありません。作者の「新しい残留行は増えていない」という説明は、この更新後の行について裏付けられません。

残留行は共有の試験データベースで試験の独立性を損ないます。例として `osf_tests/test_session.py:24–31` は 2 セッションを追加した後の総数を検査するため、残留のあるデータベースで実行すると順序に依存し得ます。今回の成功した CI が失敗した、またはその順序で実行したという主張ではありません。

**修正要求:** 利用者を削除する前に、保存しておいた利用者識別子と `data__auth_user_id` が一致するセッションをすべて削除してください。`missing_user` は JSON 内の識別子を変更するため、初期セッションの主キーによる削除も残してください。削除済みセッションへの対応と、行削除前のサーバー停止を維持してください。HTTP 全 18 ケースについて、終了後に初期行・当該利用者の全更新行・プロジェクト・利用者が残らないことを検査し、同じデータベースで続くセッション件数検査も確認してください。

### 解消した指摘と回帰確認

**R4-01:** `tests/nii/test_search_api2.py:216–226` は返された users リンクを同じ利用者の認証でたどり、`{user._id}` との完全一致と無関係な 2 人の除外を検査します。リンクの解析はパスとエンコード済みクエリを保持します。概要の件数、他の分類とリンクの既存検査も残っています。

実際の旧・新テストメソッドを抽出し、応答を模擬して実行しました。概要の利用者数は常に 1 のままにしました。旧テストは利用者一覧を要求しないため、全応答を受け入れました。新テストは本人だけなら成功し、他人 1 人、本人と他人 2 人、空一覧はすべて拒否しました。R4-01 で問題にした応答を新検査が捕捉することを独立に確認しました。作者による製品コードの一時改変試験は r4 への回答 (RDM-osf.io-dev2027 PR #8, comment 6795434539) に記録されていますが、こちらでは再実行していません。

**N1:** `test_normalize_all` の両方の再索引呼出し（764–767 行、780–783 行）が `user_pattern=del_func is _del_user` を渡します。wrapper は再索引・再試行の場合も直接実行の場合も引数を渡すため、利用者パターンでは正規化の両方向で非共有側を検査し、共有相手の正常系も維持します。`test_normalize_user_ongoing_job_school:1410–1426` の逆方向も、既定の非共有利用者を検査した後に共有相手 `user5` を検査します。既存の順方向と対応し、職歴・学歴の 6 項目の確認も維持しています。ソースを確認し、変更した呼出し構造は AST（Python が読み取ったソース構造）でも検査しました。
