### Verdict

**Changes requested: one deployment-contract issue (R1-01, P2).** The path change is correct for the ADR-06 developer environment. This is a review conclusion, not a GitHub approval or merge. The patch changes one executable line and adds four Mako comment lines.

### R1-01: provide the bundle in non-overlay deployments

Location: `addons/wiki/templates/edit.mako:737`. The new URL is unconditional. A clean deployment built only with this repository's Dockerfile or ordinary asset pipeline does not create `website/static/public/js/wiki/wiki-edit-page.js`. The editor request therefore returns 404 unless an external deployment step supplies it. The repository's Dockerfile runs its own `webpack-prod` (`Dockerfile:188`), whose wiki entry is disabled; `package.json:104` selects `webpack.prod.config.js`, which imports the active common config. Neither its Compose assets service (`docker-compose.yml:413`) nor repository-wide searches revealed a wiki overlay copier or alias creation step. Generated `website/static/public/` is ignored (`.gitignore:114`); the target directory is absent in the inspected checkout.

The known provider is specifically RDM-developer-guide's `wiki_assets`: it copies the overlay output, adds the unhashed alias, and makes it available through `wiki_static` mounted at `/code/website/static/public/js/wiki/`. That satisfies the developer environment contract; it is not evidence that a production deployment already runs it. No production environment was inspected, so this is a reproducible missing prerequisite for deployments without that provider, not a claim of an observed production outage. The old raw source also contains CommonJS `require` calls and was already unsuitable as an ordinary browser script; reverting to that source is not a working fallback.

Before treating the change as generally deployable, document and connect an equivalent production build/copy/mount or static-server publication step. It must install the overlay bundle, its `wiki-edit-page.js` alias and every required chunk under the new URL prefix before serving the changed template. If this branch intentionally supports only the developer overlay, explicitly state that deployment restriction and the prerequisite in deployment documentation. Verify the new URL and required chunks return JavaScript successfully and run C4 with the intended deployment configuration.

### Other requested checks

**References and shadowing:** a repository-wide search, including hidden configuration files but excluding Git internals, found no other active template, route, or test referring to the old URL. Translation `.po`/`.pot` files retain source-location comments. `webpack.common.config.js:37` has the wiki entry commented out. `webpack.common.config.js_org:25` retains an active entry in a backup file, but the configured build does not import that file. Automatic add-on discovery only considers `files.js`, `node-cfg.js`, `user-cfg.js`, `file-detail.js`, and `widget-cfg.js` (`webpack.common.config.js:108`); it cannot recreate `wiki-edit-page`. Consequently the current osf.io build has no same-name wiki editor bundle to shadow. Its production output remains in `website/static/public/js` (`webpack.prod.config.js:44`); mounting only the `wiki/` subdirectory preserves the other page bundles and the root asset manifest. The old raw source remains reachable through the generic static route if retained on disk; changing the template does not remove that route or file.

**Static serving:** `framework/flask/__init__.py:13–17` constructs Flask with `settings.STATIC_FOLDER` and `settings.STATIC_URL_PATH`. `website/settings/defaults.py:23–27` sets these to `website/static` and `/static`. Thus `/static/public/js/wiki/wiki-edit-page.js` maps to `website/static/public/js/wiki/wiki-edit-page.js` without a dedicated wiki route, provided the file exists and settings are not overridden. A production reverse proxy/CDN serving `/static` must publish the same subtree; its live configuration was not available.

**Mako comments:** line-leading `##` is valid single-line Mako comment syntax. The same template already uses it at line 11; the upstream Mako lexer also recognizes `##` in `match_control_line`. The four new comments are template comments, not browser-visible HTML. The unquoted constant `src` value is unchanged in form and contains no characters that require quoting for HTML parsing; no new syntax defect was found.

No build, browser/C4 run, live HTTP check, or production inspection was performed. No Docker state, application source, commits, branches, or merge/approval state was changed. The review file was checked directly with `tools.docs_check.check_file` because it is untracked.

### 判定

**要修正：配備の前提に関する指摘 1 件（R1-01、P2）。** ADR-06 の開発環境に対するパス変更は正しい。これはレビューの判定であり、GitHub の承認やマージではない。差分は実行内容 1 行の変更と Mako コメント 4 行の追加である。

### R1-01：オーバーレイを使わない配備にも束の配置手順が必要

対象：`addons/wiki/templates/edit.mako:737`。新 URL は無条件で使われる。本リポジトリの Dockerfile または通常のアセット生成だけでクリーン配備すると、`website/static/public/js/wiki/wiki-edit-page.js` は作られない。外部の配備処理で補わなければ、エディタのリクエストは 404 になる。Dockerfile は自身の `webpack-prod` を実行する（`Dockerfile:188`）が、Wiki エントリは無効である。`package.json:104` が選ぶ `webpack.prod.config.js` は有効な common 設定を読み込む。Compose の assets サービス（`docker-compose.yml:413`）およびリポジトリ全体の検索でも、Wiki オーバーレイのコピーや別名作成の処理は見つからなかった。生成先 `website/static/public/` は追跡対象外（`.gitignore:114`）であり、調査した checkout に対象ディレクトリは無い。

確認できた供給元は RDM-developer-guide の `wiki_assets` である。オーバーレイの成果物を写し、ハッシュ無しの別名を作り、`wiki_static` を `/code/website/static/public/js/wiki/` に mount して提供する。これは開発環境の前提を満たすが、本番配備でも実行される証拠ではない。本番環境自体は調査していないため、供給処理が無い配備で再現する前提不足の指摘であり、実際の本番障害を観測したという意味ではない。旧ソースにも CommonJS の `require` があり、通常のブラウザ用スクリプトとして元から不適切だった。旧パスへの復帰は動作する代替手段にならない。

一般の配備に適用可能とする前に、同等の本番ビルド・コピー・mount または静的サーバへの公開手順を文書化し、配備に組み込むこと。変更後のテンプレートを公開する前に、オーバーレイの束、その別名 `wiki-edit-page.js`、必要な全チャンクを新 URL の配下へ配置する必要がある。このブランチが開発用オーバーレイだけを対象とするなら、その制限と前提を配備文書に明記すること。意図した配備構成で新 URL と必要なチャンクが正常に JavaScript を返すこと、および C4 を確認すること。

### ほかの確認事項

**参照と隠蔽：** Git 内部を除き隠し設定ファイルも含めたリポジトリ全体の検索で、旧 URL を使う別の有効なテンプレート・ルート・テストは見つからなかった。翻訳の `.po` / `.pot` にソース位置コメントは残る。`webpack.common.config.js:37` の Wiki エントリはコメントアウトされている。バックアップ `webpack.common.config.js_org:25` には有効なエントリが残るが、設定済みのビルドはこれを読み込まない。アドオン自動検出の対象は `files.js`・`node-cfg.js`・`user-cfg.js`・`file-detail.js`・`widget-cfg.js` のみ（`webpack.common.config.js:108`）で、`wiki-edit-page` を再生成しない。そのため現行 osf.io ビルドの同名エディタ束を隠すことはない。本体の本番出力先は `website/static/public/js`（`webpack.prod.config.js:44`）のままで、`wiki/` のみの mount は他ページの束とルートのアセット一覧を保つ。旧ソースがディスク上に残れば汎用静的ルートから引き続き配信される。テンプレート変更は旧ルートやファイルを削除しない。

**静的配信：** `framework/flask/__init__.py:13–17` は `settings.STATIC_FOLDER` と `settings.STATIC_URL_PATH` を指定して Flask を作る。`website/settings/defaults.py:23–27` はそれぞれ `website/static` と `/static` を設定する。したがってファイルが存在し設定が上書きされなければ、新 URL は `website/static/public/js/wiki/wiki-edit-page.js` に対応し、Wiki 専用ルートは不要である。本番のリバースプロキシや CDN が `/static` を配信する場合も同じ下位ディレクトリの公開が必要だが、実環境の設定は確認できていない。

**Mako コメント：** 行頭の `##` は正しい一行コメント構文である。同じテンプレートの 11 行目にも用例があり、上流 Mako の lexer の `match_control_line` も `##` を認識する。追加された 4 行はテンプレートコメントであり、ブラウザに HTML として出ない。引用符の無い定数の `src` は従来と同じ形式であり、HTML 解析で引用符を必須とする文字も含まないため、新たな構文上の問題はない。
