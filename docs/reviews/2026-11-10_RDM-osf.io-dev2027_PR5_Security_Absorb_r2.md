### Verdict

**Changes requested for R1-DB (P2 / Medium).** The original R1 interleaving is repaired on the default database. R2's three ordinary HMAC comparisons and R3's Nextcloud operand mismatch are repaired. R1-DB is a new regression in the save override. R2-GL is a separate pre-existing integration defect and is not the reason for blocking this round.

### R1-DB — The transaction and row lock can use different databases

Location: `addons/twofactor/models.py:128–138`; context: `osf/db/router.py:64–82`, `api/base/settings/defaults.py:37`.

`transaction.atomic()` opens a transaction on `default`. The unqualified `select_for_update()` query and the superclass save instead follow database routing. The configured `PostgreSQLFailoverRouter` can select a writable database alias other than `default`. In that configuration, saving an existing two-factor settings object outside an outer transaction on the selected alias raises `TransactionManagementError: select_for_update cannot be used outside of a transaction`. Flask add-on deletion/reactivation and other ordinary saves do not acquire that alias's transaction through this method. An explicit `save(using=...)` also needs a matching lock and transaction.

Independent reproduction used the exact new `save()` method, two isolated SQLite connections, a router selecting `primary`, and Django's SQL compiler with `has_select_for_update=True` to exercise its transaction guard. Creation succeeds; the subsequent save raises the stated error. This is a transaction-routing reproduction, not a PostgreSQL concurrency run. Default-only deployment does not trigger it.

Resolve the effective write alias once, respecting an explicit `using` argument and otherwise the router. Use that same alias for `atomic(using=...)`, the locking queryset's `.using(...)`, and the superclass save. Add a routed/non-default database regression test. The default-database stale-save tests cannot detect this defect.

### R1 — Counter and caller review

For an unchanged secret on the default connection, the row is fetched inside `atomic()` and the lock remains held through the superclass save. The saved maximum counter wins. The conditional `verify_code()` update both enforces counter ordering and predicates on the verified secret; PostgreSQL row updates serialize against the lock. This is sound by source inspection, but actual concurrent PostgreSQL sessions were not run.

Both Flask and API setup callers now invoke `confirm_setup()` after strict verification. That method writes only `is_confirmed` and `modified`, with a secret predicate, and returns false after reset/deletion. It does not overwrite the counter or drift. The Basic/API authentication callers do not save afterward; verification itself persists the counter. The direct queryset writes found in this model are the guarded verification update and the narrow confirmation update. No other production writer of `totp_last_counter`, or bulk writer targeting this model, was found in the repository search.

Independent fixed-order checks passed for stale full saves, partial saves including the counter, confirmation-only saves, `confirm_setup()`, strict duplicate rejection, permitted same-step Basic/API reuse, and stale verification/confirmation after secret reset. Deletion prevents stale confirmation. A structural check confirmed lock-query evaluation occurs inside the default transaction. The new secret is intentionally allowed to reset the counter. The override is not a universal stale-object guard: a stale full save with a different secret can still overwrite secret state; no new production caller demonstrating that pre-existing race was identified. Direct future `QuerySet.update()`/bulk writes must preserve the invariant themselves.

### R2 and R3 — Signature checks and input types

GitHub, GitLab and conference Mailgun now call `constant_time_equals`; both `Signer` verification paths already do. The helper normalizes text and bytes to bytes and rejects missing/non-string values. Independent probes verified valid and forged signatures and spied on `hmac.compare_digest`. Missing GitHub/GitLab signature headers become an empty string and are rejected when the body has the type expected by the verifier. Actual HTTP header values are text; passing a bytes header directly to these utilities still fails at their pre-existing text `.replace()` before the helper. Mailgun's absent signature form key raises a request-form key error (Werkzeug's bad-request behavior), rather than accepting a request; a present `None` value is rejected by the helper.

Nextcloud now compares normalized operands. The exact webhook function, with request/model/task adapters, accepted a correct signature and scheduled work once; forged, non-ASCII, empty and missing signatures were rejected without scheduling. Bytes and text signatures were both covered. This independently verifies function behavior, not the complete Flask route. The author's two full-route tests were read but not independently executed.

The repository-wide source search found the other in-repository verification sites still using `compare_digest`: cron signed URLs, Crossref Mailgun, IQBRIMS, Dropbox Business and throttling. No remaining ordinary signature equality was found in the searched Python production code. This does not certify third-party verifiers or graceful handling of every malformed input; unchanged direct text comparisons in some of those paths can still raise on non-ASCII input.

### R2-GL — Existing GitLab bytes-body failure

Location: `addons/gitlab/utils.py:39`; caller: `addons/gitlab/views.py:318–321`.

The receiving view passes Flask `request.data` (bytes), but the verifier calls `data.encode('utf-8')`. A correctly signed bytes body raises `AttributeError` before comparison. Independent execution reproduced the same failure at both r1 and r2 heads, so it is not introduced by these commits. Existing utility tests supply text and receiving-view tests mock the verifier. Normalize the body without re-encoding bytes and add an unmocked webhook-route test in a follow-up; otherwise the GitLab constant-time tests do not establish working request integration.

### R1-DB — トランザクションと行ロックの DB が一致しない場合がある

対象: `addons/twofactor/models.py:128–138`。関連: `osf/db/router.py:64–82`、`api/base/settings/defaults.py:37`。

`transaction.atomic()` は `default` 上でトランザクションを開始する。一方、接続指定のない `select_for_update()` と親クラスの保存は DB ルーターに従う。設定されている `PostgreSQLFailoverRouter` は `default` 以外の書き込み可能な接続を選ぶ場合がある。その構成で選択先の外側トランザクションがなければ、既存の二要素認証設定の保存が `TransactionManagementError: select_for_update cannot be used outside of a transaction` になる。Flask のアドオン削除・再有効化や通常保存では、このメソッドで選択先のトランザクションを確保できない。明示的な `save(using=...)` も同じ接続のロックとトランザクションが必要である。

新しい `save()` 本体をそのまま使い、独立 SQLite 接続二つ、`primary` を選ぶルーター、`has_select_for_update=True` とした Django SQL コンパイラーのトランザクション検査で再現した。新規作成は成功し、その後の保存で該当例外になる。これは接続振り分けの再現であり PostgreSQL の並行実行試験ではない。既定接続のみの配備では発生しない。

明示的な `using` 引数を優先し、それ以外はルーターから実際の書き込み接続名を一度だけ決めること。同じ接続名を `atomic(using=...)`、ロック対象 queryset の `.using(...)`、親クラスの保存に渡すこと。既定以外へ振り分ける回帰試験を追加すること。既定 DB の古いインスタンス保存試験では、この不具合を検出できない。

### R1 — カウンタと呼び出し元

既定接続上で秘密値が変わらない場合、行の取得は `atomic()` 内にあり、親クラスの保存終了までロックを保持する。保存済みの大きいカウンタが優先される。`verify_code()` の条件付き更新はカウンタの順序と検証した秘密値を条件に持ち、PostgreSQL の行更新は行ロックと直列化される。ソース上は妥当だが PostgreSQL の実並行セッションでは試していない。

Flask・API の設定確認はどちらも厳密検証の後に `confirm_setup()` を呼ぶ。同メソッドは秘密値を条件に `is_confirmed` と `modified` だけを更新し、秘密値の再設定・削除後は false を返す。カウンタや drift を上書きしない。Basic/API 認証の呼び出し元は後続保存をせず、検証自体がカウンタを永続化する。このモデル内で見つかった queryset 直接更新は、条件付きの検証更新と確認用の限定更新である。リポジトリ検索では他の製品コードの `totp_last_counter` 書き込みや、このモデルを対象にした一括更新は見つからなかった。

順序を固定した独立試験では、古い全フィールド保存、カウンタを含む部分保存、確認フィールドのみの保存、`confirm_setup()`、厳密モードでの重複拒否、Basic/API 用の同一ステップ再利用許可、秘密値の再設定後の古い検証・確認拒否が成功した。削除後の古い確認も拒否した。構造検査ではロック用 query が既定トランザクション内で評価されることを確認した。新しい秘密値でカウンタをリセットするのは意図した動作である。この上書きは古いオブジェクトを全面的に防ぐものではなく、秘密値が異なる古い全フィールド保存は秘密値自体を上書きできる。この既存競合を示す新しい製品呼び出し元は確認していない。将来の `QuerySet.update()` や一括書き込みは自身で単調性を維持する必要がある。

### R2・R3 — 署名検証と入力の型

GitHub・GitLab・conference Mailgun は `constant_time_equals` を使うようになった。`Signer` の二経路も既に同じヘルパーを使う。ヘルパーは text と bytes を bytes に統一し、欠落値や文字列以外を拒否する。独立試験で正しい署名・偽造署名と `hmac.compare_digest` の呼び出しを確認した。GitHub/GitLab の署名ヘッダー欠落は空文字列になり、本文が検証関数の想定する型なら拒否される。実 HTTP ヘッダー値は text である。ユーティリティへ bytes のヘッダーを直接渡す場合は、既存の text 用 `.replace()` でヘルパー到達前に失敗する。Mailgun の署名フォームキー欠落は要求フォームのキーエラー（Werkzeug の bad-request 動作）となり、要求を受理しない。キーが存在して値が `None` ならヘルパーが拒否する。

Nextcloud は型をそろえて比較する。要求・モデル・タスクのアダプターを使って webhook 関数本体を実行し、正しい署名では一回だけ処理を予約し、偽造・非 ASCII・空・欠落署名では予約せず拒否した。bytes と text の署名を確認した。これは関数の独立検証であり Flask のルート全体の試験ではない。作成者が追加したルート試験二件は読んだが独立実行していない。

リポジトリ全体のソース検索では、他の検証箇所である cron 署名 URL、Crossref Mailgun、IQBRIMS、Dropbox Business、throttling は引き続き `compare_digest` を使う。検索した Python 製品コードに通常の署名等値比較は残っていなかった。外部ライブラリの検証や全不正入力の正常なエラー処理まで保証しない。変更されていない一部の直接 text 比較は非 ASCII 入力で例外になり得る。

### R2-GL — GitLab の bytes 本文の既存不具合

対象: `addons/gitlab/utils.py:39`。呼び出し元: `addons/gitlab/views.py:318–321`。

受信 view は Flask の `request.data`（bytes）を渡すが、検証関数は `data.encode('utf-8')` を呼ぶ。正しく署名した bytes 本文でも比較前に `AttributeError` となる。r1 と r2 の両 head で同じ失敗を独立再現したため、今回のコミットが導入した問題ではない。既存のユーティリティ試験は text を渡し、受信 view の試験は検証関数を mock にしている。bytes を再 encode しない本文正規化と、検証を mock にしない webhook ルート試験を追跡対応すること。現在の GitLab 定数時間比較試験だけでは実要求との統合動作を証明できない。
