### Authorization and internal host disclosure

`addons/base/views.py:1098–1102` calls `check_contributor_auth` and returns a login response before constructing the WaterButler redirect. WaterButler is the service that retrieves stored files. `mode=render` is a routing hint, not authentication and not proof that the requester is MFR. For a private node, an anonymous JSON request without an active view-only token is rejected with 401; an unauthorized signed-in user is rejected with 403. Neither response carries a WaterButler Location. An anonymous browser request follows the existing login path instead. File and version API views likewise check object permissions before returning serialized links (`api/files/views.py:42–61, 70–77, 148–169`).

**An anonymous or non-contributor user can obtain an internal WaterButler URL for a public file, and can also do so for a private file when holding an active view-only link.** This is authorized read access, not a contributor bypass. Knowing a private file identifier or passing `mode=render`, `_internal`, or `base_url` alone does not grant access. The unchanged WaterButler authentication callback still checks file access; a redirect URL is not a signed grant or a new credential.

The API deliberately discloses `INTERNAL_DOMAIN` inside the encoded `url` argument of `links.render`, including for publicly readable files. The outer origin remains the configured browser-facing MFR address. The browser requests that outer URL; MFR, the file preview service, fetches the internal OSF URL and follows its internal WaterButler redirect. A client should not directly dereference the inner `web:5000` address. This is meaningful in the intended network layout and matches the legacy page's existing exposure (`addons/base/views.py:1151–1167`). I consider that topology disclosure acceptable for this server-side change: these names are not secrets and access does not depend on hiding them. It is not a claim that internal hostnames remain confidential.

The checked-in installer config pairs `http://web:5000` with `http://wb:7777` and includes both in MFR's permitted destinations. Browser-side PDF/image fetching still relies on the existing MFR local-development host conversion and reachable public WaterButler configuration; `PdfRenderer._render` uses `munge_url_for_localdev`. Real reachability and alternate port mappings were not tested. This PR does not make arbitrary internal URLs usable in browsers.

`addons/base/views.py:1104–1114` は `base_url` を削除し、`_internal` を厳密な `mode == 'render'` の結果で上書きする。要求元は既存の描画経路を選べるが、ホストを指定できない。それ以外の mode は従来の公開 WaterButler の選択を保持し、osfstorage ではリージョンのアドレスを使う。同名クエリが重複した場合は、既存の `request.args.to_dict()` の先頭値採用に従う。`api/base/utils.py:207–218` は設定からホストを取り、モデルに由来するパスを加え、残りの要求値をクエリのデータとして扱う。新たな open redirect（攻撃者が指定した任意ホストへの転送）は見つからなかった。修正前の `_internal=1` による内部ホスト選択と、`base_url` の引数衝突は、このエンドポイントでは解消される。

描画 URL の生成には URL 専用の符号化、モデルの識別子、固定の描画引数を使う（`api/files/serializers.py:536–576`）。細工した `view_only`・`url`・`_internal`・`base_url` で MFR の取得元ホストは置き換わらない。版の描画リンクは `revision` を保持し、通常の download・HTML リンクは公開ドメインを保持する。

統合済み MFR PR #7 のソース `2c4a88a663ca2c659e2b8fe46a2f26e84f206ba9` も読んだ。今回の OSF 変更は MFR の許可先一覧や資格情報の付与を変えない。MFR は最初と転送後の取得先を検証し、自動転送を無効にし、設定された厳密な送信元・送信先の組だけに別 origin への資格情報を許す。対象の組では、MFR が捕捉した Authorization・cookie・cookie クエリ・view-only を OSF から WaterButler へ付与できる。別の保存先をネットワーク上で許可するだけでは、それらの自動転送される資格情報を付与する権限は得られない。この変更による新たな SSRF（サーバーに意図しないネットワーク先を取得させる攻撃）の経路は見つからなかった。この評価は内側の URL の秘匿ではなく、既存 MFR の検証と信頼された配備設定を前提とする。

### View-only、旧 C5、Ember の後続対応

有効な view-only トークンは引き続き永続ダウンロード経路を許可し、WaterButler のクエリにも保持される。トークンなし、失効済み、不正な値では非公開ファイルの権限を得られない。追加試験は細工したトークンの URL 構造を検査しているが、有効／失効した実際の view-only リンクを API → MFR → OSF → WaterButler 全体へ通す試験ではない。

Ember の後続対応では既存の制約に注意が必要である。`get_file_render_link` は内側のクエリを置き換え、API の描画リンクは外側の MFR クエリにも `view_only` を付けない。この欠落は base と head の補助関数の両方で再現した。MFR は自分の外側のクエリに渡されたトークンを転送する。そのため、匿名の view-only 閲覧者に対しては API リンクをそのまま iframe に設定するだけでは足りず、クライアントが安全にトークンを引き継ぐか、リンクの契約を拡張する必要がある。その後続対応で、有効／失効した view-only の結合試験を追加したい。PR #14 が導入した権限回帰ではなく、範囲を限定したサーバー側前提変更の必須修正とはしない。

旧 C5 経路は自分で内部 URL を作り、`addon_view_or_download_file` を使う。同関数と `addon_view_file` は base とプログラム構造が同一である。通常の `/download/<id>/` は、明示的な render mode 以外では公開側を保持する。描画時に全体設定の内部 WaterButler を選ぶ動作は旧経路と同じであり、独立した複数リージョンを持つ配備では別途経路確認が必要となる。

Ember `d3caa8a` の renderer は `links.download` から MFR の入力を作り、`links.render` は使わない。そのため最初の要求先は依然としてブラウザ向け OSF アドレスになる。永続ダウンロード経路には Ember の画面選択デコレータもなく、旧 GUID 経路で MFR が必要とする転送の代わりに HTML が返る問題を避けられる。PR #14 は意図されたサーバー側の2変更として妥当かつ十分だが、Ember プレビューの成功を主張するには不足する。残るクライアント変更では認証・view-only・版の指定も保持する必要がある。実機 C5 は実行しておらず、ソースの維持や単体試験をブラウザ受入の代わりにはしない。
